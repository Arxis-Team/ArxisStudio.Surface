# 16. Пины и провода выполнения: вид даёт библиотека, смысл — хост

Дата: 2026-09-29
Статус: Принято. Базовый вид выполнения и делегата и `PortShape?` у `PinShape` — ADR 0017.

## Контекст

В Blueprint два вида пинов. Пины выполнения (Exec, белый пятиугольник) и провода между ними задают
порядок: движок идёт по белой линии, а Branch, Sequence и циклы её ветвят, повторяют и обрывают. Пины
данных (круги цвета типа) отвечают на вопрос «что», и узлы чистых данных пинов выполнения не имеют:
их значения считаются, когда выполнение доходит до узла, который их спрашивает. Провод выполнения
толще провода данных. Владелец попросил поддержать то же, оставив дизайн за разработчиком: пины
выполнения не обязаны быть белыми.

Смысл пина — правило графа. Редактор узлов его не знает, как не знает типов данных (ADR 0004): он
соединяет порты по ключам, а что с чем соединять, решает хост в `ConnectValidating`. Не хватало вида:
штырёк был зашит в шаблон порта кругом с кистями темы, толщина провода — одна на всех.

## Решение

**Библиотека даёт вид, хост — смысл.** Вида пина выполнения или типа «выполнение» в API нет. Есть
три свойства вида, и хост ставит их по своему графу:

- `Port.PinShape` — `Circle`, `Execution` (пятиугольник остриём вправо), `Square`, `Diamond`,
  `Triangle`, `Custom` с `Port.PinGeometry`. Шаблон рисует `Path` с геометрией `Port.PinData`,
  вписанной с сохранением пропорций; центр штырька — конец связи, как прежде.
- `Port.PinBrush` — обводка пустого штырька и заливка подключённого, как у пинов Blueprint. Без неё —
  кисти темы. Согласие и отказ протягиваемой связи красят обводку поверх неё: обратная связь жеста
  важнее цвета вида.
- `NodeEditor.LinkThicknessBinding` — толщина провода из модели, рядом с `LinkStrokeBinding`: провод
  выполнения толще провода данных. Запись связи держит толщину, контрол связи её берёт, рамка и
  попадание считаются по ней.

Свойства порта — обычные стилевые: хост ставит их привязкой к модели порта или стилем по классу
(`surface|Port.exec`). Оба пути равноправны; образцы показывают оба.

**Порядок выполнения и правила — у хоста.** «Выполнение только к выполнению», «из выхода выполнения
одна связь, во вход — сколько угодно», «во вход данных одна» — правила `ConnectValidating` (образец —
`GraphDocument.CanConnect` демо). Обход выполнения — модель хоста; импульсы по проводам (ADR 0014)
показывают его так же, как в Blueprint.

## Отвергнуто

- **Тип порта «выполнение» в библиотеке** (`Port.Kind = Execution` со встроенными правилами). Библиотека
  начала бы решать граф хоста: сколько связей из выхода, что с чем соединимо. У машины состояний все
  порты — поток управления, у графа данных выполнения нет вовсе; правило одно не бывает.
- **Классы связи из модели (`LinkClassesBinding`) вместо толщины.** Классы видит только развёрнутый
  контрол связи; запись без контрола — упрощённый вид, рамка, попадание — их не знает. Толщина в записи
  работает для всех, кроме упрощённого слоя и миникарты, которые рисуют провода одной толщиной.
- **Кисть штырька отдельно для обводки и заливки.** Пин Blueprint — один цвет в двух состояниях; хосту,
  которому нужно иначе, остаётся своя тема порта.

## Последствия

- Штырёк порта — `Path`, а не `Ellipse`: стиль хоста, писавший `Ellipse#PART_Pin`, больше не применится;
  селектор — `Path#PART_Pin` или просто `#PART_Pin`.
- Геометрия фигур создаётся при первом обращении: тип порта грузится и без платформы отрисовки.
- Демо узлов: событие «Каждый кадр» → «Вывод» → «Журнал» по белым проводам выполнения толщиной 3,5,
  пины — пятиугольники; узлы данных без пинов выполнения; пины данных — цвета типа; правила соединения —
  как в Blueprint. Машина состояний: все её порты — поток управления, пятиугольники заданы стилем по
  классу `flow`.
- Тесты (`ExecutionPinTests`): форма из порта и своя геометрия; кисть обводит пустой штырёк и заливает
  подключённый; отказ протягиваемой связи сильнее кисти; толщина провода из модели, её смена по
  `PropertyChanged` и возврат к теме.
