# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Команды

```bash
dotnet build ArxisStudio.Surface.sln      # сборка решения
dotnet test tests/ArxisStudio.Surface.Tests/ArxisStudio.Surface.Tests.csproj
dotnet run --project samples/UiDesigner.Demo # запуск демо дизайнера интерфейса
dotnet run --project samples/Nodes.Demo        # запуск демо редактора узлов
```

Один тест: `dotnet test --filter "FullyQualifiedName~SelectionTests.Click_On_Nested_Control_Selects_It_As_Nested_Target"`.

Тесты — headless-UI на `Avalonia.Headless.XUnit`. Важно: этот пакет завязан на **xunit v3**, не на v2. Атрибуты `[AvaloniaFact]` / `[AvaloniaTheory]` вместо `[Fact]` / `[Theory]`: они поднимают headless-приложение из `TestAppBuilder` и загоняют тело теста в UI-поток.

`Avalonia.Headless` умеет настоящий ввод — `MouseDown`/`MouseUp`/`MouseWheel`/`KeyPress` на `Window` — и `SetRenderScaling` для проверки DPI-путей. Поэтому клик-поведение выделения проверяется автоматически, без запуска окна.

Тесты писать **на наблюдаемое поведение** (`SelectedTargets`, `PrimarySelectionTarget`, `SelectionBounds`, счётчики), а не на внутренние структуры выбора: `_selectionTargets` будет переписан при переходе к рекурсивной вложенности, а ожидания должны пережить рефакторинг.

`EditorHarness.Create` выключает привязку к сетке (`snapToGrid: false`), хотя в боевой конфигурации она включена. Тесты перетаскивания и контракта изменений проверяют механику, а не привязку, и не должны ломаться от «сдвинули на 60 — получили 70». Сам факт включённости по умолчанию закреплён отдельно в `SnapToGridTests`; там же harness создаётся с `snapToGrid: true`. `NestedContainerTests` выключает её в своём `Create`.

По той же причине и тем же способом выключено выравнивание по соседям (`snapToGuides: false`): в шаблоне стенда рядом с `Nested` стоит `Sibling`, и любой сдвиг, подошедший к нему ближе радиуса захвата, менял бы результат тестов, проверяющих совсем другое. Умолчание закреплено в `SnapGuideTests`, и стенд для них собран свой — с соседями разного размера, чтобы выравнивание по краю, по центру и по противоположному краю проверялись порознь.

Контейнеры реализуются только после layout-прохода — в тестах его прогоняет `EditorHarness.RunLayout()` через `GetLayoutManager()`. Без него `Bounds` пустые и выделение не резолвится.

Каждая сборка открывает internals тестам и сборкам выше себя через `InternalsVisibleTo` в своём `Properties/AssemblyInfo.cs` — подробнее в разделе «Слои».

Демо остаётся для визуальной проверки рендера и тем — этого headless не покрывает. Оттуда же сняты скриншоты README корня и дизайнера интерфейса (`docs/images/`): пересобирать их надо после правок, меняющих вид — шапки, оверлеев, направляющих. Снимок берётся у **самого окна** через `PrintWindow`, а не с экрана: `CopyFromScreen` копирует пиксели по координатам, то есть всё, что лежит сверху, и всплывающее уведомление чужого приложения уезжало бы в репозиторий — это уже случилось однажды. Ключ `-Screen` возвращает захват с экрана и нужен ровно там, где содержимое лежит в отдельном окне (контекстное меню Avalonia — popup, `PrintWindow` главного окна его не видит); там перед копированием проверяется Z-порядок, и чужое окно над демо снимок отменяет. Скиллы в `.claude/skills/`: `run-demo` (запуск демо, скриншот, клик, двойной клик, drag с модификаторами и зум по координатам окна, клавиши) и `avalonia-api` (сверка API между версиями Avalonia по пакетам NuGet).

У демо есть канал управления для проверки API вживую: `--automation <каталог>`. Он кладёт в каталог два файла — команда `command.json` и ответ `response.json` — и исполняет команды на UI-потоке. Без аргумента ничего не поднимается: ни таймера, ни подписок, ни файлов.

```bash
./samples/UiDesigner.Demo/bin/Debug/net10.0/UiDesigner.Demo.exe --automation "$A" &
printf '%s' '{"name":"select","target":"PART_Border"}' > "$A/command.json"; sleep 0.5; cat "$A/response.json"
```

Команды: `state`, `tree`, `select`, `selectContainer`, `clearSelection`, `setSelectedIndex`, `addSelectedItem`, `nudge`, `zorder`, `viewport`, `guides`, `group`, `groups`, `events`. Ответ несёт оба слоя выделения и точные числа, поэтому проверяется не «похоже на правильное» по скриншоту, а конкретное значение. Запускать нужно **собранный exe**, а не `dotnet run` из шелла: процесс, породивший его, умирает вместе с командой и уносит демо.

Чем это отличается от двух других способов проверки: headless-тест закрепляет поведение, скриншот проверяет рендер, канал отвечает на вопрос, что получает живой хост, вызывая публичный API. Все четыре дефекта выделения из этапа 2 плана были воспроизведены именно им — с числами, а не по картинке.

Сборка должна проходить с **0 предупреждений**. У библиотеки включён `GenerateDocumentationFile`, поэтому любой новый публичный член без XML-doc даёт CS1591.

Если сборка падает с `MSB3021`/`MSB3027` («файл используется другим процессом») на `ArxisStudio.Surface*.dll` — это **не ошибка кода**, а блокировка от `Avalonia.Designer.HostApp` (XAML-превьюер Rider). Компиляция при этом проходит; ломается только копирование в выходной каталог демо. Лечится закрытием вкладки превью или `taskkill /PID <pid> /F`. Проверить код в обход блокировки:

```bash
dotnet build src/Surface.UiDesigner/ArxisStudio.Surface.UiDesigner.csproj
```

Он собирает три библиотеки из четырёх — ядро и инструменты он называет ссылками; редактор узлов
собирается так же своим проектом, `src/Surface.Nodes`.

## Состав решения

| Проект | TFM | Назначение |
|---|---|---|
| `src/Surface/ArxisStudio.Surface.csproj` | `net8.0` | ядро: холст, viewport, сетка, контейнер, выделение, жесты, контракт изменений |
| `src/Surface.Editing/ArxisStudio.Surface.Editing.csproj` | `net8.0` | инструменты: ручки, привязка, направляющие, линейки, миникарта |
| `src/Surface.UiDesigner/ArxisStudio.Surface.UiDesigner.csproj` | `net8.0` | дизайнер интерфейса: `UiDesignerView` — окна, `UserControl`, шаблоны и формы |
| `src/Surface.Nodes/ArxisStudio.Surface.Nodes.csproj` | `net8.0` | редактор узлов: `NodeEditor`, узлы, порты, связи |
| `samples/UiDesigner.Demo` | `net10.0` | демо дизайнера интерфейса, `AvaloniaUseCompiledBindingsByDefault = true` |
| `samples/Nodes.Demo` | `net10.0` | демо редактора узлов — хост на одном публичном API, свой `CLAUDE.md` |

Общее у четырёх библиотек — TFM, документация, метаданные пакета — лежит в `src/Library.props`, и каждая импортирует его одной строкой.

Avalonia UI **12.1.1**. `net8.0` у библиотек — это минимальный TFM, поддерживаемый Avalonia 12 (netstandard2.0 больше не поставляется); понижать нельзя.

`global.json` задаёт **нижнюю границу**, а не точную версию: `10.0.100` и `rollForward: latestMajor`. Собрать `net10.0` может любой SDK от .NET 10 и новее, и именно это условие и стоит записывать.

Точная версия здесь была ошибкой, и она не «предупреждала о несовпадении», а ломала всё: `rollForward` катится вперёд, но не назад, поэтому на машине с 10.0.1xx при закреплённых 10.0.301 переставала работать любая команда `dotnet` в каталоге репозитория — не только сборка, но и `dotnet --version`.

`.external/` — справочный материал: клоны [nodify](https://github.com/miroiu/nodify) и его
порта на Avalonia. В решение они не входят, не собираются и **не отслеживаются** — каталог
в `.gitignore`. Нужны — положить руками:

```bash
git clone https://github.com/miroiu/nodify .external/nodify
```

Отслеживались они ровно один раз и зря: `git add` попал на каталог, который сам является
репозиторием, и git молча записал в индекс gitlink. Секции в `.gitmodules` при этом не
появилось — файла здесь нет вовсе. Собственную сборку это не задевало, а рекурсивный клон
головного ArxisStudio ломало наглухо, ещё и молча для того, кто правит эту библиотеку:

```
fatal: No url found for submodule path '.external/nodify' in .gitmodules
fatal: Failed to recurse into submodule path 'external/ArxisStudio.DesignEditor'
```

### Упаковка

```bash
dotnet pack ArxisStudio.Surface.sln -c Release -o artifacts
```

Пакетов четыре — `ArxisStudio.Surface`, `ArxisStudio.Surface.Editing`, `ArxisStudio.Surface.UiDesigner`, `ArxisStudio.Surface.Nodes`, — и зависимости в них идут вниз, как ссылки проектов: дизайнер интерфейса и редактор узлов тянут инструменты и ядро, инструменты — ядро. `IsPackable` выключен в `Directory.Build.props` и включён обратно в `src/Library.props`: иначе рядом ложились бы пакеты тестов и демо.

Тема едет **внутри сборки**: AXAML каждой библиотеки компилируется в неё, и в пакете нет ничего, кроме `lib/net8.0` и README. Проверено потреблением — проект на `net10.0`, подключивший `.nupkg` из локального фида, видит у сборки ресурс `!AvaloniaResources`.

README у каждого пакета свой — из папки его проекта (`src/<слой>/README.md`, `PackageReadmeFile` в `src/Library.props`): корневой README описывает семейство и выбор слоя, README сборки — её API и поведение. Новый публичный член документируют в README своей сборки, а не в корневом.

Символы идут отдельным `.snupkg`, а не внутри пакета. SourceLink с .NET 8 SDK встроен и ссылки на пакет не требует; в `.nuspec` он проявляется элементом `repository` с хешем коммита — по нему и проверять, что он сработал.

Версия `0.x` осознанно: публичная поверхность закреплена слепком, но всё ещё меняется, а `1.0` обещает совместимость, которую сейчас обещать нечем.

Правообладатель — **ArxisStudio**; отсюда же `Authors`, `Company` и `Copyright` в метаданных пакета. Лицензия — MIT, задана SPDX-выражением `PackageLicenseExpression`, а не файлом: для стандартной лицензии это рекомендованный способ, и NuGet сам подставляет ссылку. Файл `LICENSE` в корне остаётся для людей и для GitHub.

В NuGet библиотека **не публикуется** — это решение, а не отложенный пункт. Иконки в пакете тоже нет.

## Слои

Библиотека делится на три слоя — ADR 0003, там же причина и «почему не иначе». Первый этап развёл
их по папкам и пространствам имён внутри одной сборки, второй — по **трём сборкам и трём пакетам**.
Четвёртый слой — редактор узлов — встал рядом с дизайнером интерфейса, а не над ним (ADR 0004).
Следом за пакетами переименован и репозиторий: был `ArxisStudio.DesignEditor`, стал
`ArxisStudio.Surface` (прежний адрес GitHub перенаправляет). У головной студии он лежит в
`external/ArxisStudio.Surface`, а образец `FormsDesigner` в ProjectSystem ищет его соседом под
этим же именем. Типы после этого ещё несли приставку монолита, и ADR 0006 привёл их к слоям:
`Design*` стали `Surface*`, дизайнер — `UiDesignerView` с контейнером `UiDesignerItem`, описания
правок — `TargetChange` и наследники, демо — `UiDesigner.Demo`, ключи темы — `Surface.*` и
`UiDesigner.*`. Таблица соответствия — там же. Новому типу приставку даёт библиотека (`Surface`), а
главному контролу слоя — слой (`<Слой>View`, `<Слой>Item`).

| Слой | Пространство имён и сборка | Папка |
| --- | --- | --- |
| ядро: холст, viewport, сетка, контейнер, выделение контейнеров, рамка, жесты, координаты, контракт изменений | `ArxisStudio.Surface` | `src/Surface/` |
| инструменты: ручки, привязка, направляющие, линейки, миникарта, распределение, z-order, блокировки | `ArxisStudio.Surface.Editing` | `src/Surface.Editing/` |
| дизайнер интерфейса: `UiDesignerView`, вложенные target'ы, `Layout`, стратегии размещения, перестановка, группы | `ArxisStudio.Surface.UiDesigner` | `src/Surface.UiDesigner/` |
| редактор узлов: `NodeEditor`, узлы, порты, связи, протяжка, выбор и отцепление связей | `ArxisStudio.Surface.Nodes` | `src/Surface.Nodes/` |

Ссылки идут только вниз: ядро не называет ни инструменты, ни слои над ними, инструменты не называют
ни дизайнер интерфейса, ни редактор узлов, а сёстры — дизайнер интерфейса и редактор узлов — не называют друг
друга. Всё, что ядру нужно знать сверху, оно получает через шов. Между сборками направление
держит уже сам компилятор — ссылок проектов вверх нет, — а внутри сборки и в тестах его держит
`LayerDependencyTests`: по пространствам имён, с разбором тел методов, и строго. Тип вне четырёх слоёв
роняет его так же, как ссылка вверх, а тип, лежащий не в сборке своего слоя, — так же, как тип вне слоёв.

**Швы остались internal**, и сборки выше видят их через `InternalsVisibleTo`: ядро открывает
internals инструментам, дизайнеру интерфейса и редактору узлов, инструменты — дизайнеру интерфейса и редактору
узлов, все четыре — тестам. Это осознанно: публичный шов — обещание, а формы у швов проверены пока
двумя потребителями из одного репозитория. Публикацию когда-то обещали под редактор узлов, но он
оказался в этом же репозитории и видит швы так же (ADR 0004); публиковать их придётся под первого
редактора извне — и тогда же внести в baseline.
Компилятор XAML дружественные сборки уважает: тема дизайнера интерфейса называет internal-типы
инструментов (`SelectionAdornerLayer`) и собирается.

Правило для нового кода: **если код ядра называет `Layout`, `ContentMode`, панель Avalonia или
группу — он не в ядре.**

**Ядро работает само, без дизайнера интерфейса**, и держит это `SurfaceViewTests` — набор на голом
`SurfaceView`, без единого `UiDesignerView`. Пока его не было, ядро было отделено только на бумаге:
у `SurfaceView` не было ни темы, ни своих контейнеров, ни панели, которая ставит их в
`Location`, — поверхность не рисовала ничего, и ни один тест этого не видел, потому что все шли
через дизайнер интерфейса. Когда тема появилась, всплыли ещё четыре дыры, и все одного рода — общее
жило у дизайнера интерфейса:

- **публикации выделения не было**: `RefreshSelectionOverlay` в ядре был пуст, выбор писался, но
  `SelectedTargets` и событие молчали;
- **`SelectionMode = Multiple`** ставил конструктор `UiDesignerView`, и рамка на голом ядре
  оставляла выбранным один элемент из двух;
- **единицу правки перетаскивания открывал обработчик дизайнера интерфейса** (`OnItemsDragStarted` и
  соседи), и без него состояние перетаскивания считало жест отклонённым — теперь они в ядре
  (`SurfaceView.ItemDrag.cs`), а правило дизайнера про смешанную группу — хук
  `BlocksSelectionDrag`;
- **нажатие по невыбранному элементу уходило рамке**: правило «пустая область формы — рамке»
  считало пустым весь контейнер, у которого резолвер не предлагает кандидатов. У ядра их нет
  никогда — контейнер сам единица выбора, — и `ShouldDeferPressToMarquee` уступает рамке только
  там, где внутри контейнера вообще есть что выбирать.

Тема ядра не называет ни одного ключа слоёв выше — это `The_Core_Theme_Needs_No_Other_Layer`
проверяет текстом. Наследнику `SurfaceView` без своей темы нужен `StyleKeyOverride`: Avalonia
ищет тему по точному типу.

Первый этап закончен: ни одного типа вне слоёв. Швы ядра и их реализации:

| Шов ядра | Что спрашивает | Дизайнер интерфейса | Инструменты |
| --- | --- | --- | --- |
| `ISurfaceGeometry` | где target, можно ли задать позицию, его рамка | `SurfacePlacementGeometry` | — |
| `ISurfaceTargetResolver` | кандидаты внутри контейнера и кто из них выбирается | `NestedTargetResolver` | — |
| `ISurfaceInteractionPolicy` | что разрешено двигать и тянуть, пересечением | `PlacementMovePolicy` | `SurfaceInteractionLockPolicy` |
| `IEditFacet` | что ещё входит в единицу правки | `GroupEditFacet` | — |
| `ISurfacePositionModifier` | куда встаёт предложенная позиция или край | — | `SnapService` |
| службы `AddService`/`GetService` | подключаемые инструменты | — | `SnapService`, `UserGuideService` |
| виртуальные хуки `SurfaceView` | клик по контейнеру, решение о протяжке, контекст, брошенный жест, ключ группы | переопределяет | — |

Свойства инструментов — присоединённые у их классов (`SurfaceSnapping`, `SurfaceGuides`), а
`UiDesignerView` берёт их через `AddOwner`: шаблон и привязки видят их как собственные. Историю ядро
не ведёт, но даёт готовую — `SurfaceHistory` поверх `ISurfaceChange`.

Что второму этапу стоит знать. В `UiDesignerView` осталось общее, а не формовое: сборка оверлея и
политики адорнеров, обработчики ручек resize, z-order и распределение. Клавиатура из этого списка
уже ушла в ядро набором команд (см. «Клавиатура»). Слой их — инструменты, и граница соблюдена: `UiDesignerView` вправе называть и ядро, и
инструменты. Но редактору, который не наследует дизайнер интерфейса, их придётся либо вынести в службы,
либо написать заново; выносить их стоит под первого такого потребителя.

## Архитектура

### Где что лежит

Редактор — два класса: `SurfaceView` в ядре (`src/Surface/`) и его наследник `UiDesignerView` в
дизайнере интерфейса (`src/Surface.UiDesigner/`). Оба разбиты на `partial`-файлы по темам. Инструменты
лежат в `src/Surface.Editing/` службами и контролами.

`SurfaceView` — `SurfaceView.cs`: оба конструктора, переэкспорт индексного выбора, привязки положения и
полосы элемента (`ItemLocationBinding`, `ItemAccentBinding` — ADR 0009), сигнал смены содержимого
(`ContentChanged`), реестр служб, сетка из шаблона. Остальное:

| Файл | О чём |
| --- | --- |
| `SurfaceView.Viewport.cs` | положение, масштаб, обе трансформации и их DPI, зум колесом, `CenterOn*`/`FitToView`, `ItemsExtent` |

### Три системы координат

Это главный источник ошибок в этом коде. Не путать:

1. **Координаты контрола** — `e.GetPosition(editor)`, пиксели viewport'а.
2. **Мировые координаты** — `editor.GetWorldPosition(p) == p / ViewportZoom + ViewportLocation`. В них считаются marquee, group drag delta и hit-testing.
3. **Координаты поверхности** — `Layout.SurfaceX` / `Layout.SurfaceY`, положение относительно поверхности дизайна. В них живут `SelectionBounds`, adorner'ы и результат drag/resize.

`UpdateTransforms()` строит **два** transform group'а: `ViewportTransform` (точный) и `DpiScaledViewportTransform` (со смещением, округлённым до физического пикселя через `TopLevel.GetTopLevel(this)?.RenderScaling`). Второй нужен фону и сетке, чтобы линии не размывались. Менять один без другого нельзя.

Group drag намеренно считается по **накопленной world-space delta** от начальной точки, а не по текущей layout-позиции source target — иначе смещение «плывёт» при ненулевом зуме.

### Двухуровневое выделение

`UiDesignerView : SelectingItemsControl`, поэтому штатная модель Avalonia (`Selection`, `SelectedItems`) оперирует **контейнерами** `UiDesignerItem`. Поверх неё редактор ведёт собственный слой выбора вложенных контролов:

- `_selectedTargets: List<Control>` — плоский список target'ов в порядке приоритета: первый это primary

Контейнер, выбранный целиком, — это просто сам `UiDesignerItem` в этом же списке; отдельной структуры под него нет. (Раньше здесь были описаны `_selectionTargets: Dictionary<…>` и `_containerSelectionTargets: HashSet<…>` — их в коде нет давно, а искать по ним приходилось.)

Отсюда следует, что **`SelectedItems.Count` ≠ `SelectedTargetsCount`**: один выбранный контейнер может содержать несколько выбранных nested targets. Публичный контракт выбора — `SurfaceSelectionTarget` (`Container`, `Target`, `Scope`, `DisplayName`); `Scope` различает `Container` и `NestedTarget`.

Оба слоя пишет одна точка — `ApplySelection`. Не все: у неё **один** target на вызов, а коммит рамки пишет набор, собранный по нескольким контейнерам, одной транзакцией, и разложить его на вызовы по одному target'у нельзя, не потеряв гарантию одного события. Поэтому `CommitSelection` и `CommitMarqueeWithinContainer` батчат оба слоя сами; согласованность у них измерена и закреплена в `SelectionCoherenceTests` — восемь сценариев, включая вложенные контейнеры, где разошлись бы резолверы владельца, если бы расходились. До неё правило «слои меняются вместе» держала каждая точка записи своими руками, с разными резолверами владельца и разным набором guard'ов; отсюда и брались состояния, которые указатель построить не может, а публичный API строил. Путь указателя тоже переведён на транзакцию: индексный слой писало состояние контейнера, слой target'ов — редактор уже после, и между двумя записями оверлей успевал пересобраться.

Порядок здесь оказался неочевидным и стоил одного отката. Неявный ответ `ResolveSelectionTargets` («item выбран, target не назван — значит выбран его первый ребёнок») **держал** гарантию «одно событие на клик»: промежуточный снимок случайно совпадал с итоговым, и второе событие гасилось сравнением. Поэтому чтение нельзя было исправить первым — сначала запись одной транзакцией, потом чтение. В обратном порядке один клик начинал поднимать два события.

Схлопывание группы **контейнеров** обычным кликом отложено на **отпускание** намеренно: иначе группу нельзя было бы потащить — она распалась бы на нажатии. Правило смотрит на индексный слой (`Selection.Count > 1`), поэтому группу вложенных target'ов внутри одной формы обычный клик не схлопывает вовсе — он только меняет primary; это тоже намеренно и закреплено в `SelectionTests`. Поэтому такой клик стоит двух событий, и оба описывают настоящие изменения: на нажатии сменился primary, на отпускании схлопнулась группа. Проверять тут надо не число событий, а что наружу не публикуется состояние, которого не было: до транзакции событий было три, и одно объявляло пустое выделение между двумя записями индексного слоя.

Два слоя выбора обязаны меняться вместе. `_selectedTargets` держит target'ы, а `Selection` — индексы item'ов, и оверлей обходит именно `SelectedItems`, спрашивая у каждого его targets. Контейнер, попавший в `Selection` без собственной записи в `_selectedTargets`, подменяется вложенным target'ом по умолчанию — и группа контейнеров молча превращается в смешанную. Именно так и ломался `Ctrl + Shift + Click`: ветка контейнера всегда заменяла выбор, второй контейнер вытеснял первый, а первый возвращался в оверлей уже своим вложенным контролом. Правки в одном слое без другого делать нельзя — см. `SyncContainerItemSelection`.

В режиме `Annotated` nested target'ом может стать только контрол с designer-метаданными — см. `HasLayoutMetadata` (наличие `Layout.X/Y` или `Layout.IsTracked`); отбор идёт через `IsSelectableTarget`, который знает режим контейнера. Клик по «нетрекаемой» области внутри контейнера сбрасывает nested target и переводит выбор на уровень контейнера; fallback-выбора «первого tracked контрола» больше нет — это осознанное поведение, не баг.

### Группы

Группа — **пометка на контролах**, а не узел дерева. Причина не в экономии: редактор дерево не правит (ADR 0001), и контейнер, созданный им, изменил бы проекцию, не изменив источник. Если группа нужна контейнером в разметке — это работа хоста.

#### Где лежит пометка

**Редактор владеет смыслом группы, а местом хранения — тот, кто владеет документом** (ADR 0002). Между ними шов `ISurfaceGroupStore` и свойство `UiDesignerView.GroupStore`; внутри библиотеки чтение сведено в `GetGroupOf` рядом с единственной точкой записи `SetSurfaceGroup`.

Причина измерена: из четырёх значений, которые редактор пишет в чужие контролы, у трёх есть читатель в рантайме (`Layout.X`/`Y` читает `AbsolutePanel`, `Width`/`Height` и `ZIndex` — сама Avalonia), а у группы нет ни одного. Соседние пометки — `SurfaceInteraction` и `Layout.IsTracked` — рантайм-смысла тоже не имеют, но их редактор **не пишет никогда**: они появляются в файле, только если их набрал автор. Группа была единственным значением, которое редактор записывал в чужой документ сам, — а вместе с ним туда уезжали и зависимость на сборку редактора, и грамматика пути как часть формата.

Умолчание — `SurfaceGroupAttachedStore`, то самое attached-свойство `ArxisStudio.Surface.UiDesigner.SurfaceGroup.Id`: пометка лежит на контроле, пишется руками в разметке и сохраняется тем же способом, что и `Layout.X`/`Y`. Поэтому шов ничего не ломает.

Ключ хранилища — **сам контрол**, и живёт он столько же, сколько загруженная форма. Хранилищу, которое переживает перезагрузку разметки, нужен ключ документа: в `ArxisStudio.Markup` это узел и путь к нему, а перевод «контрол ↔ узел» делает хост через `XamlObjectMap`. Так уже устроен `FormsDesigner` из `ArxisStudio.ProjectSystem` — он держит группу своим `d:DesignGroup` в документе, — и до появления шва ему приходилось **зеркалить** её в attached-свойство на каждой загрузке.

**Пометка — это путь**, от внешней группы к внутренней: `SurfaceGroup.Id="group-2/group-1"` читается как «участник `group-1`, которая лежит в `group-2`». Плоская пометка остаётся валидной — это путь из одного сегмента, поэтому чужие макеты и разметка демо продолжают работать без правок. Разделитель `/` — часть контракта: в сегменте его быть не может, и проверяют это точки записи (`GroupSelection`, `RenameGroup`), а не `SurfaceGroup.SetId` — сырое присваивание остаётся сырым.

Личность группы — **весь путь**, а не последний сегмент: одинаковые имена уровней на разных ветках не сталкиваются. Арифметика пути вынесена в `Grouping/SurfaceGroupPath`, потому что разбирают его трое — группировка, оверлей и жесты.

Отсюда третий шов записи рядом с `SetTargetPosition`/`SetTargetSize`/`SetTargetZIndex` — `SetSurfaceGroup`, — и третий вид правки `SurfaceEditKind.Group` с `GroupChange`. Отмена и повтор применяют её через `ApplyGroup`, как геометрию через `ApplyGeometry`.

#### Кластеры

Выделение — не плоский список target'ов, а набор **кластеров**. Кластер это то, что пользователь видит одной рамкой: группа целиком на видимом сейчас уровне либо одиночный контрол. Считает их `BuildClusters`, и точка эта одна на всех потребителей — оверлей, группировку, роспуск: своя копия правила в оверлее однажды уже была, и это ровно тот случай, когда показанное расходится с применённым.

Состав каждой группы считается **одним обходом формы** (`CountGroupMembers`): полноту кластера и совпадение выделения с группой спрашивают на каждом кадре жеста, и обход по разу на кластер и на уровень пути вернул бы зависимость от размера макета — ту самую, из-за которой у рамки выделения появился снимок контейнеров.

Группа образует кластер, **только если выбраны все её участники**, включая вложенные уровни. Иначе рамка обещала бы жест над тем, чего в выделении нет; выбранные её участники идут отдельными кластерами. Указателем половину группы не выбрать, а публичным `SelectTarget` — можно, и тест на это есть.

**Раскрытие до кластера — свойство клика, а не замены выделения.** `Shift + Click` по участнику чужой группы добавляет её целиком, повторный — убирает целиком. Первая версия раскрывала только неаддитивную ветку, и к выбранной группе добавлялся один контрол из другой: на экране появлялась третья рамка там, где элементов двое. Выделение при этом не опустошается — то же правило, что у обычного toggle одного target'а.

Правила операций, каждое закрыто тестом в `NestedGroupingTests`:

- **Группировка считает кластеры, а не target'ы.** Выбранная целиком группа — один кластер, и новый уровень над ней в одиночку ничего не разделяет: нужно не меньше двух кластеров. Прежде плоская модель на этом месте просто выдавала группе новый идентификатор.
- **Группа-участник вкладывается, а не растворяется.** Её путь сохраняется хвостом, а новый уровень встаёт над **общим префиксом** родительских путей всех кластеров — он определён всегда, поэтому отказа «разные уровни» не нужно.
- **Хвост сохраняет только кластер-группа.** Одиночный контрол группой не является и входит в новую напрямую: пока он ребейзился как все, уровень, из которого его вытащили, уезжал с ним и превращался в фантомную группу с тем же именем, что и настоящая. Наполовину выбранная группа кластером не становится, поэтому её участник — именно одиночный контрол.
- **Роспуск снимает один внешний уровень.** Вложенные группы переживают его и поднимаются на уровень выше; дробить их заодно значило бы разрушить структуру, собранную отдельным действием.
- **Только вложенные target'ы одной формы.** Контейнер группировать нечем — он и так одна рамка, а принадлежность к форме задаёт `ItemsSource`.

Показ: у кластера-группы рисуется **одна** рамка. Единственный кластер-группа — это прежний случай «выделение равно группе», его рисует `PART_GroupSelectionAdorner` под `HasGroupSelection`. Несколько кластеров — по адорнеру на кластер в `SecondarySelectionAdorners`, у группы с `Role = Group`. Так и получается то, ради чего кластеры заводились: выбранные группа и сосед дают две рамки, а не столько, сколько внутри контролов.

**Всё, что смотрит на рамку всего выделения, обязано смотреть через `ShowsGroupFrame`.** Таких мест три: показ в шаблоне, политики в `UpdateSelectionAdornerPolicies` и вход в жест в `OnGroupSelectionResizeStarted`. Первая версия научила рамку показываться, а два других места оставила на `HasMultipleContainerSelection` — и это дало два симптома с одной причиной. Locked-визуал не отдельное оформление, а то, как рисуется adorner с политиками `None`/`None`.

Жесты кластера идут через ту же `GroupResizeOperation`, только состав ей передаётся явно: ручки рамки группы масштабируют её одну, а сосед рядом распоряжается своей рамкой сам. **Обработчики вторичных адорнеров ветвятся по составу адорнера, а не по полю операции** — тому же условию, что и на входе в жест: незакрытая операция кластера иначе перехватывала бы следующий пожатийный resize одиночного контрола. Потеря захвата закрывает групповой жест там же, где разбирается стек состояний, и **фиксирует** его единицу редактирования: геометрия к этому моменту уже применена. Политики кластера складываются пересечением — заблокированный участник запирает весь кластер, то же правило, по которому смешанная группа locked/unlocked не двигается вовсе.

#### Вход в группу

**Вход** — повторный клик по тому же месту; `_enteredGroupPath` держит открытый уровень. Первый клик берёт самую внешнюю группу, второй входит в неё и берёт вложенную целиком, третий — сам контрол. Проваливаться сразу до контрола нельзя: тогда промежуточные уровни указателем не выбрать, а вход в группу ради работы внутри неё и заводился. Закрывается вход в одном месте, `SyncEnteredGroup` на пересборке оверлея: перечислять все точки смены выбора значило бы их все и найти, а клик по пустому холсту в этом списке уже терялся.

**Уровень показа задаёт форма выделения, а не только указатель.** Выбран ровно состав какой-то группы — значит смотрим на неё снаружи, и открытым остаётся её родитель; берётся при этом самая внешняя подходящая группа. Без этого правила вход, открытый двойным кликом, переживал выбор, сделанный **не указателем**: панель групп выбирает состав по одному target'у через `SelectTarget` и об открытом уровне не знает, поэтому клик по строке группы разбивал её на отдельные контролы — вместо одной рамки пользователь получал четыре. Второе правило прежнее: вход закрывается, когда из его группы не осталось ничего выбранного.

Клик по участнику раскрывается до его кластера в `ApplyTargetFromPoint` — там же, где указатель выбирает target. Раскрытие и оверлей обязаны совпадать, поэтому точка одна (`ExpandToGroup`).

Пакетная запись выделения (`ApplySelection(IReadOnlyList<Control>, …)`) заведена здесь же: план откладывал её до появления потребителя, и потребитель — группа. Клик по участнику обязан выбрать всех сразу, а разложить это на вызовы по одному target'у нельзя, не потеряв гарантию одного события.

#### Чтение

**Чтение — запрос, а не снимок.** `GetGroups(container)` отдаёт дерево групп верхнего уровня (вложенные — в `SurfaceGroupInfo.Groups`), `GetGroupMembers(container, path)` — весь состав по пути, включая вложенные уровни. Считается по дереву в момент вызова. Все остальные публичные чтения библиотеки устроены наоборот — свойство со снимком, публикуемое по сравнению, — и группам такая форма не годится: деревом владеет хост, пометку он вправе поставить в разметке или через `SurfaceGroup.SetId`, и узнать об этом редактору неоткуда. Кэш протух бы молча.

О чужих правках сообщает **хранилище**, а не редактор: `ISurfaceGroupStore.GroupsChanged` пересобирает оверлей. Умолчание его не поднимает никогда и не притворяется — за attached-свойством оно не следит, и это ровно то поведение, что было до шва. Подписка на событие **слабая**: хранилище хост заводит одно на документ, а редакторов над одним документом бывает несколько, и обычная подписка сделала бы хранилище держателем всех — та же ошибка, что уже была с общим набором жестов.

`SurfaceGroupInfo.Members` — контролы, лежащие в группе **непосредственно**; вложенные уровни лежат в `Groups`, а весь состав целиком отдаёт `GetGroupMembers`. Ключ группы — пара «контейнер + путь», поэтому контейнер стоит параметром, а не подразумевается.

**Участником считается только то, что редактор даёт выбрать.** Отбор один на всех потребителей и стоит в `EnumerateGroupCandidates`; его наследуют раскрытие по клику, роспуск и публичное чтение. Раньше фильтра не было вовсе, хотя этот документ уже утверждал обратное: в режиме `Annotated` контрол, помеченный хостом, но без designer-метаданных, попадал в состав, и клик по соседу раскрывал выделение на то, что указатель выбрать не может.

Исключение из этого правила ровно одно, и снимать его нельзя: **подбор и проверка занятости обходят без фильтра** (`NextGroupId`, `IsGroupPathTaken`). Они отвечают на вопрос «занято ли имя», а невидимая редактору пометка занимает его не меньше видимой — новая группа, вставшая на чужой путь, слилась бы с ней при первом же сохранении.

**Переименование — это правка, а не свойство.** `RenameGroup(container, path, newId)` меняет **один сегмент** пути у всех участников одной единицей редактирования, через тот же шов, что и группировка: иначе смена имени не попала бы в `EditCompleted`, и отмена вернула бы всё, кроме него. Переезд в другого родителя — это перемещение группы, отдельное действие. Имя обрезается по краям на самом шве, а не в панели: правила имени обязаны жить в одном месте, иначе « toolbar » и «toolbar» станут двумя внешне неотличимыми группами. Отклоняется в трёх случаях, и каждый — ответ, а не ошибка вызывающего: имя пустое или содержит разделитель, такой группы в форме нет, либо среди её **братьев** идентификатор занят — последнее означало бы слияние двух групп, а слияние обязано быть отдельным действием.

Вход в группу переезжает вместе с именем: `_enteredGroupPath` держит путь, и оставь его прежним — группа осталась бы «открытой» по имени, которого больше нет.

`SurfaceSelectionTarget.GroupId` читается при создании снимка, и поэтому `AreSameTargets` сравнивает пару `(Target, GroupId)`. Правило прежнее — **публикуется всё, что сравнивается**: группировка уже выбранного набора не меняет ни состав, ни порядок, и сравнение по одним target'ам признало бы снимок неизменившимся; хост остался бы со старой группой при верном экране.


### Контейнер как хост загруженной формы

`UiDesignerItem.ContentMode` различает два происхождения содержимого.

`Annotated` (по умолчанию) — шаблон написан вместе с приложением, и автор сам решает, что редактируется: target'ом становится только контрол с `Layout.IsTracked` или `Layout.X/Y`.

`Loaded` — форма пришла целиком, например из `.axaml`. Размечать её некому, поэтому редактируется вся авторская разметка, а содержимое перестаёт реагировать на ввод.

Два следствия, оба выяснены замером:

- **Обход идёт по авторским связям, а не по визуальному дереву.** `EnumerateAuthoredContent` спускается только по детям панели, ребёнку декоратора и контенту, если это контрол. Проверки `TemplatedParent` **недостаточно**: презентер порождает из строкового контента `AccessText`, у которого `TemplatedParent` пуст, и клик по кнопке выбирал бы её надпись.
- **Ввод гасится на `PART_ContentPresenter`** стилем `^[ContentMode=Loaded]`, а не обходом дерева. Выделение от этого не страдает: попадание считается по прямоугольникам в мировых координатах (`TryResolveSelectionTargetAtPoint`), а у самого контейнера фон `Transparent` на всю площадь, поэтому нажатие достаётся ему. Без гашения выделения не возникает вообще — живая кнопка обрабатывает нажатие сама, и до контейнера оно не доходит.

Стратегии размещения с загруженной формой работают без изменений: корень разметки — обычная панель Avalonia, и редактор сам определяет, двигать ребёнка, переставлять или не трогать.

Вся пересборка состояния выделения проходит через `UpdateSelectionOverlayState()` → `TryGetSelectedTargetBounds(...)`. Это единственная точка, где обновляются `SelectionBounds`, `SecondarySelectionAdorners`, `HasSingle/Multiple*Selection` и `SelectedTargets`.

### Две независимые машины состояний

Обе — стек с `PushState` / `PopState`, и они не связаны друг с другом:

- **Уровень редактора** — `EditorState` (`src/Surface/States/`): `EditorIdleState`, `EditorPanningState`, `EditorSelectingState` в ядре, `EditorGuideDraggingState` в инструментах. `SurfaceView.OnPointer*` делегирует в `CurrentState`.
- **Уровень контейнера** — `SurfaceItemState` (`src/Surface/States/SurfaceItemStates.cs`), стек живёт в `SurfaceItem`: `ItemIdleState` и `ItemDraggingState` в ядре, `ItemResizingState` в инструментах, `ItemReorderingState` в дизайнере интерфейса. У базового класса есть `ReEnter(...)` — вызывается при возврате из вложенного состояния, — и `PseudoClass`: состояние само называет псевдокласс, которым контейнер его показывает, потому что контейнер ядра не знает состояний, которые приносят слои выше. Что делать с протяжкой, `ItemIdleState` спрашивает у поверхности (`PlanItemDrag`).

**Захват указателя принадлежит жесту, а не шаблону.** `EditorSelectingState` и `EditorPanningState` захватывают указатель в `Enter` и снимают в `Exit`. Avalonia на нажатии захватывает сама, но достаётся захват тому, что попало под указатель, — в шаблоне это `Border`, и доставка зависела бы от формы шаблона. Главное же — потерю захвата теперь видит редактор: `SurfaceView.OnPointerCaptureLost` разбирает стек до базового состояния, тем же приёмом, что и контейнер.

Без этого брошенная рамка оставалась на стеке навсегда и держала `IsSelecting`, а по нему `OnItemsDragStarted` отклонял следующее перетаскивание — при том что контейнер об отказе не узнавал и продолжал писать геометрию каждый кадр с закрытой единицей редактирования. Правка уходила мимо undo. Прежний комментарий в `EditorPanningState`, утверждавший, что захватывать не нужно, и был причиной.

**Базовому состоянию о потере захвата говорят отдельно.** Вложенные состояния узнают о ней через `Exit` — контейнер разбирает стек, — но базовое со стека не снимается никогда, и до появления `SurfaceItemState.OnPointerCaptureLost` оно о брошенном жесте не узнавало вовсе: `_isPressed` оставалось поднятым, то есть следующее движение указателя над контейнером начинало перетаскивание без нажатия. Заметили это на курсоре запрета, который иначе оставался бы на контейнере навсегда.

**Отклонённый жест не пишет геометрию.** `ItemDraggingState` после `DragStarted` спрашивает `HasActiveEdit`: `e.Handled` для этого не годится — редактор ставит его на всех ветках, включая успешную, а открытая единица есть только на успешной. После правки захвата достижимых отказов не осталось, так что проверка стоит как защита шва, а не как исправление живого дефекта.

**Осиротевшая единица редактирования фиксируется, а не затирается.** В `BeginEdit` стояло простое присваивание, и если предыдущий жест не закрыл свою единицу, следующий уничтожал её молча. Поздняя запись хуже своевременной и несравнимо лучше потерянной. Достижимый путь утечки построить не удалось — правка тоже защитная.

Групповые операции вынесены из состояний в `GroupDragOperation` / `GroupResizeOperation` (оба реализуют внутренний `IInteractionOperation`). Правила для nested-группы централизованы в снимке `SelectionInteractionCapabilities` — в частности `CanMoveNestedGroup` и `HasMixedMovePolicies` (смешанная группа locked/unlocked не двигается вообще).

### Слои шаблона

Шаблон `UiDesignerView` (`src/Surface.UiDesigner/Themes/UiDesignerView.axaml`) разделён на слои. Самый нижний — `PART_Grid` (`SurfaceGrid`), остальные три — Canvas:

- `PART_ItemsLayer` — содержимое (`PART_ItemsPresenter` + `AbsolutePanel`)
- `PART_SelectionOverlayLayer` — `PART_SelectionAdorner` (primary), `PART_GroupSelectionAdorner`, `PART_SecondarySelectionAdorners` (`SelectionAdornerLayer`)
- `PART_InteractionOverlayLayer` — временные оверлеи на время действия пользователя (marquee и индикатор точки вставки при перестановке)
- `PART_SnapGuideLayer` — направляющие выравнивания (`SnapGuideLayer`)

`SurfaceGrid` и `SnapGuideLayer` — слои **без** `ViewportTransform`. Он получает `ViewportLocation` и `ViewportZoom` напрямую и рисует в экранных координатах: только так толщина линий остаётся пиксельной на любом масштабе, а уровни детализации могут скрывать мелкую сетку. Не пытаться навесить на них трансформацию — это сломает оба свойства. Направляющая, растущая вместе с зумом, перестаёт быть указателем и начинает закрывать макет.

`SnapGuideLayer` визуального дерева не строит вовсе — только `Render`. Это осознанно: у слоя, который перестраивает детей, уже была история с пропадающими оверлеями внутри layout-прохода, и повторять её было не за чем.

`UiDesignerItem` **не рисует** рамку выделения и ручки — всё это editor-level. Не возвращать item-level selection-свойства в контейнер.

`SelectionAdornerLayer` не должен менять visual tree во время `Measure`/`Arrange` — это уже приводило к пропадающим secondary overlays при `Shift + Click` (см. коммит 98c8f0d). Перестроение делать вне layout-прохода.

### Attached-свойства `Layout`

`ArxisStudio.Surface.UiDesigner.Layout` двусторонне синхронизирует локальные `X`/`Y` (относительно родителя) и глобальные `SurfaceX`/`SurfaceY`:

- `X`/`Y` или `IsTracked` включают подписку на `LayoutUpdated` → пересчёт `SurfaceX`/`SurfaceY`
- запись в `SurfaceX`/`SurfaceY` идёт обратно в локальные координаты
- рекурсия гасится внутренним `IsUpdatingPosition`
- если контрол ещё не в visual tree, пересчёт откладывается до `AttachedToVisualTree`

Два уточнения, которые важны при отладке:

- `UpdateSurfacePosition` **всегда** идёт через `Dispatcher.UIThread.Post(..., DispatcherPriority.Render)`. То есть `SurfaceX`/`SurfaceY` не «иногда», а гарантированно отстают на один проход диспетчера от фактического layout. Читать их сразу после установки `X`/`Y` бессмысленно.
- В `OnSurfacePositionChanged` из результата `TranslatePoint` вычитается `control.Margin`. `Layout.X`/`Y` — это позиция слота в родительской панели, а `TranslatePoint` возвращает визуальный top-left, уже включающий margin. Без вычитания отступ переприменялся бы на каждом следующем arrange.

### События выделения

`ApplySelectionSnapshot` — единственная точка публикации выделения. Она сравнивает новый снимок с текущим и при совпадении не делает **ничего**: ни присвоения свойств, ни события.

Это не оптимизация, а условие корректности. `UpdateSelectionOverlayState` вызывается из двух десятков мест, включая каждый кадр перетаскивания, и пересобирает снимок всегда. Без проверки `SurfaceSelectionChanged` срабатывало бы десятки раз за жест, а `SelectedTargets` переприсваивался бы новым списком, заставляя все привязки пересчитываться.

Сравнение идёт по `SurfaceSelectionTarget.Target`, а не по обёрткам: `CreateSelectionTargetsSnapshot` создаёт их заново при каждом вызове, поэтому сравнение по ссылке на обёртку всегда даёт «изменилось». Порядок значим — первый элемент это primary.

Имя события намеренно не `SelectionChanged`: оно уже занято `SelectingItemsControl` и работает на другом уровне.

### Клавиатура

Клавиатура — набор команд `SurfaceView.KeyCommands` (`SurfaceKeyCommand`, `src/Surface/Keyboard/`), а не `switch`: по нему же приложение добавляет свои команды, заменяет встроенные по идентификатору и снимает их. Нажатие проходит набор по порядку, и обрабатывает его первая команда, которая его **узнала и выполнилась**. Отказ — не ошибка, а уступка: команда приложения на стрелке, которой сейчас делать нечего, обязана отдать нажатие встроенному смещению, и именно поэтому узнавание и исполнение разделены. Обходится снимок набора, а не он сам: команда вправе поменять набор, пока её исполняют, и живой обход упал бы на первой же такой правке — мутация это подтвердила. История стоит первой, потому что её сочетание настраивается и заранее не известно.

**Изменение размера с клавиатуры** — команда `surface.resize`, клавиатурная замена ручкам (WCAG 2.2, «Dragging Movements»): стрелки с `KeyboardResizeModifiers` (по умолчанию `Alt`) двигают правый или нижний край, левый верхний угол стоит. Стоит она **до** смещения: `Alt` + стрелка — всё ещё стрелка, и смещение иначе забрало бы её первым. Правила переписаны с ручки по одному и каждое закрыто тестом в `KeyboardResizeTests`, потому что результат не должен зависеть от того, чем его добивались: политика стороны, ограничение формой (растущий упирается, уже вылезший задним числом не ужимается), предел жеста, который останавливает сжатие, но не раздувает уже мелкое, и `Min`/`Max` на шве. Привязки нет — как у смещения, клавиатура задаёт шаг точно. Выбранная группа меняется потаргетно, каждый своим размером; масштабировать рамку группы целиком по-прежнему умеют только её ручки. `None` в `KeyboardResizeModifiers` выключает команду: без модификатора изменением размера стала бы каждая стрелка.

`SurfaceView.OnKeyDown` пропускает уже обработанные нажатия — иначе стрелки и Delete отбирались бы у вложенного редактируемого контрола, если фокус в нём.

Неочевидное: `FocusableProperty.OverrideDefaultValue<UiDesignerView>(true)` фокус **не даёт**, он лишь разрешает его получить. Без явного `Focus()` в `OnPointerPressed` клавиатура до редактора не доходит вообще. Вызов обёрнут в проверку `IsKeyboardFocusWithin`, чтобы не отбирать фокус у вложенного контрола.

Нюдж идёт через тот же `BeginEdit`/`CommitEdit`, что и перетаскивание: одно нажатие — одна запись. Фильтр no-op в `SurfaceEditScope` сам отсекает случай, когда все targets заблокированы политикой.

Отмена и повтор устроены так же и по той же причине: стека правок у редактора нет. Он сообщает о своих изменениях через `EditCompleted` и умеет применить одно из них (`Revert`/`Reapply`), но что отменять и в каком порядке — знает только тот, кто их копил. Отсюда `UndoRequested` / `RedoRequested` с тем же правилом обхода подписчиков.

Сами сочетания по умолчанию берутся у платформы — `PlatformHotkeyConfiguration.Undo` / `.Redo` через `this.GetPlatformSettings()`, а `InputGestures.UndoGestures` / `RedoGestures` их перекрывают целиком, если у приложения своё соглашение. Заданный список **заменяет** платформенный, а не дополняет: иначе выключить системное сочетание было бы нечем. Это не политика редактора, а соглашение системы: на macOS это Cmd, а не Ctrl, и повтор там пишется иначе. Свои свойства под это завести значило бы разойтись с остальным приложением. Проверяется **весь список** сочетаний: в нём обычно два — `Ctrl + Y` и `Ctrl + Shift + Z`.

Клавиша без модификатора историю не трогает. Первая версия ветки повтора была написана как `case Key.Y:` без условия, и обычная «Y» вызывала бы повтор; на это есть отдельный тест.

Delete не удаляет, а поднимает `DeleteRequested`: коллекция принадлежит хосту. Если обработчика нет или он не выставил `Handled`, нажатие остаётся необработанным и всплывает дальше. Обход подписчиков останавливается на первом выполнившем — как и у `ReorderRequested`, и по той же причине: список targets снят до правки, и следующему он описывал бы выделение, которого уже нет.

### Стратегии размещения

Главное архитектурное решение библиотеки после сетки. `src/Surface.UiDesigner/Placement/`, namespace `ArxisStudio.Surface.UiDesigner.Placement`, **всё internal** — форму рано фиксировать публично, тест `Placement_Strategies_Are_Not_Public` это сторожит.

Таблица возможностей снята с реальной Avalonia 12 в `LayoutHonourProbeTests` и определяет всё остальное:

| | явный `Width`/`Height` | `Layout.X`/`Y` |
|---|---|---|
| `AbsolutePanel` | honours | **honours** |
| `Canvas`, `StackPanel`, `Grid`, `DockPanel`, `WrapPanel`, `Border` | honours | игнорирует |

Два следствия, оба неочевидные:

- **Размер honours любая панель, включая `HorizontalAlignment="Stretch"`.** Явный размер применяется до выравнивания. Поэтому resize осмыслен везде, и выводить `ResizePolicy` из раскладки не нужно — в стратегию размер не входит вовсе. Ограничивают размер `Min`/`Max` контрола и границы формы, а не родитель.
- **`Layout.X`/`Y` читает единственное место во всей библиотеке** — `AbsolutePanel.ArrangeOverride`. Даже `Canvas` их игнорирует, ему нужны `Canvas.Left`/`Top`.

`SurfaceMoveSemantics`: `Reposition` (позицию можно задать), `Reorder` (нельзя, но осмысленна перестановка среди соседей), `None` (раскладка владеет положением полностью). `SurfacePlacementResolver.Resolve` — `GetVisualParent()` и switch по типу, без кеша.

`AbsolutePlacementStrategy` обслуживает и контрол **без родителя**: на нём стоят `GroupResizeOperationTests`, которые держат `Border`'ы вне дерева ради чистой арифметики. Семантика для detached обязана совпадать с прежней — иначе падают пять snap/group-тестов.

Композиция политик — одно правило: **`effective = user & layout`**. Раскладка задаёт потолок, политика пользователя сужает, ни одна не расширяет другую. Иначе редактор снова начал бы предлагать жест, который ничего не делает. Все интеракционные точки спрашивают `GetEffectiveMovePolicy`; сырые `GetMovePolicy`/`GetResizePolicy` остались для контракта attached-свойств.

Отсечка стоит на **шве**: `SetTargetPosition` отбрасывает target, позицией которого владеет раскладка. Это единственная точка записи, значит только там можно гарантировать, что в контракт изменений не попадёт перемещение, которого не произошло. До этого drag контрола в `StackPanel` не двигал ничего и при этом писал `Move` в стек отмены.

### Перестановка среди соседей

Там, где `MoveSemantics` равна `Reorder`, перетаскивание меняет **порядок детей** — единственное, что вообще меняет их положение в потоковой раскладке. Состояние `ItemReorderingState`, выбор состояния делает `ItemIdleState`.

Перестановка применяется **на отпускании**, а не покадрово: если двигать ребёнка вживую, панель переливается под курсором и элемент прыгает. Во время протяжки рисуется индикатор точки вставки в `PART_InteractionOverlayLayer` — слой ровно под это и заводился.

Толщина индикатора **нулевая в мировых координатах**, видимую задаёт шаблон через `MinWidth`/`MinHeight` внутри обратного трансформа. Так линия остаётся одинаково тонкой на любом масштабе.

Точка вставки ищется по **обеим** осям: берётся ближайший сосед, и только потом сторона выбирается вдоль потока. В `WrapPanel` с переносом одной оси мало — оба ряда проецируются на один отрезок, и точка в нижнем ряду сравнивалась бы с серединами верхнего. В однорядной раскладке вторая ось на выбор влиять не должна, поэтому правило одно на оба случая.

Расстояние при этом считается **до прямоугольника** соседа, а не до его центра, и это не мелочь. По центрам поперечная ось начинает соревноваться с продольной, и ответ зависит от того, за какое место схватили элемент: в колонке широких строк узкая кнопка внизу прижата влево, её центр по X близок к левому краю строк — указатель у левого края оказывался ближе к ней, чем к центрам самих строк, и точка вставки уезжала в конец списка. Взятый за правый край тот же элемент вставал верно. Замер: одна и та же протяжка вниз давала индекс 2 от левого края и 1 от центра и от правого; по прямоугольнику все три дают 1. Поперечная ось теперь только отсекает чужие ряды, а внутри ряда решает продольная — как и было задумано.

Сам редактор дерево **не правит**: на отпускании он поднимает `ReorderRequested` и ждёт, пока обработчик пометит запрос `Handled`. Структурная правка — зона `ArxisStudio.Markup` (см. «Границы ответственности»), поэтому у перестановки нет ни шва записи, ни единицы редактирования: в `EditCompleted` она не попадает.

Четыре правила запроса, каждое закрыто тестом:

- **Нет подписчика — нет жеста.** `ItemIdleState` спрашивает `CanRequestReorder` до входа в состояние. Вести точку вставки за курсором, зная, что на отпускании ничего не произойдёт, — то же самое, что предлагать заблокированное перемещение.
- **Обе половины запроса снимаются за одно чтение.** Состояние отдаёт точку вставки как есть, а перевод в индекс переноса делает `RequestChildIndex` — там же, где читает текущую позицию. Раньше состояние переводило по своему снимку, снятому на входе в жест, и при изменении дерева во время протяжки хост получал пару индексов от разных состояний панели.
- **Обход подписчиков останавливается на первом выполнившем.** Индексы сняты до правки, поэтому следующему они описывали бы дерево, которого уже нет: на двух обработчиках одинаковой формы перестановка молча отменяла сама себя.
- **Точка вставки вне границ отклоняется, а не подгоняется.** `insertBefore` описывает ту же коллекцию, которую редактор прочитал: от нуля до числа детей включительно. Всё, что вне, значит, что дерево изменилось внутри жеста, и запрос не отправляется вовсе. Раньше там стоял `Math.Clamp`, и хост получал валидный на вид индекс, ставивший контрол мимо цели, — заметить это он не мог.
- **Результат читается.** `CommitReorder` возвращает его в `e.Handled` отпускания — как и `DeleteRequested`. Иначе `Handled` был бы свойством, которое никто не читает.

Кроме индексов запрос несёт `Anchor` — ссылку на соседа, перед которым встаёт контрол. Индекс осмыслен только против той же коллекции `Panel.Children`, которую редактор измерил; библиотека разметки владеет исходным деревом, где узел может не иметь ровно одного соответствия среди визуальных детей.

После выполненного запроса редактор сбрасывает targets, покинувшие дерево, и пересобирает оверлей: обработчик вправе не переставить контрол, а пересобрать разметку, и рамка, оставшаяся на контроле вне дерева, рисовалась бы по его последним координатам и принимала бы на него нюдж.

### Дельта resize отсчитывается от ручки

Самая неочевидная вещь в этом коде, и она уже один раз стоила прыгающей рамки.

`Thumb.DragDelta` в Avalonia отдаёт смещение **относительно самой ручки**, а не от точки нажатия. Замер в `ThumbDeltaProbeTests`:

| | дельты за три шага по 10 |
|---|---|
| ручка неподвижна | 10, 20, 30 |
| ручка едет следом | 10, 10, 10 |

Ручка стоит на краю выделения, то есть на **применённой** геометрии. Значит всё, что съели привязка к сетке, `Max` или границы формы, вернётся в следующей дельте повторно.

Отсюда правило: **дельты resize накапливать нельзя.** `ItemResizingState` и `GroupResizeOperation` считают от уже применённой геометрии и прибавляют пришедшую дельту, а применённое запоминают у себя — читать его обратно через `GetTargetPosition` нельзя, оно отстаёт на layout-проход. Раньше оба накапливали дельты от исходного размера: пока ничто не ограничивало resize, это совпадало, но вместе с привязкой и ограничением по форме остаток начал складываться сам с собой, и ширина шла `110, 130, 110, 130`.

**Саму дельту редактор считает от указателя, а не от ручки.** Приращённой она бывает лишь пока между двумя движениями проходит layout; стоит указателю обогнать раскладку — и `Thumb` отдаёт накопленное, а сложенное растит размер квадратично. Живой замер до правки: протяжка на 20 пикселей давала +116, на 40 и 60 — +259 и +421, то есть `s·N(N+1)/2` для десятка движений.

Смысл величины при этом не изменился — это по-прежнему «насколько указатель убежал от применённого края», поэтому остаток, съеденный привязкой или ограничением, возвращается следующим движением и элемент не отстаёт от курсора. Изменилось, чем этот остаток измеряется: раньше положением ручки, теперь самим указателем. Редактор помнит его в `PointerSample` (туннельный обработчик с `handledEventsToo`: во время жеста указатель захвачен ручкой), а состояние и групповая операция держат смещение захвата — ручку берут не за край, а за её середину.

Снимок несёт не только положение, но и **устройство** с **номером движения**, и оба поля нужны — каждое закрывает ошибку, уже сделанную в первой версии правки. Пользоваться указателем можно, только если **то же** устройство двинулось **после** начала жеста (`TryGetGesturePointer`). Без номера снимок переживал жест: хост, поднявший `ResizeStarted`/`ResizeDelta` сам — а это публичные routed-события, — сравнивался с положением, где мышь побывала до жеста, получал нулевую поправку и молча переставал что-либо менять. Без устройства перо, зависшее над холстом, пока мышь тянет ручку, увело бы край к перу. Не прошедший проверку жест считает по `e.Delta`, как раньше.

Неподвижный край тоже берётся из текущей геометрии, а не из исходной: тогда он остаётся на месте весь жест, даже когда размер во что-нибудь упёрся.

Масштаб группы при этом считается от **исходной** рамки, а не от текущей — иначе округления копились бы от кадра к кадру и группа расползалась.

### Ограничение размера контейнером

`InteractionOptions.IsResizeContainedToParent`, включено по умолчанию. Границей выбран **владеющий `UiDesignerItem`**, а не прямой родитель: панель, которая растёт по содержимому, границей быть не может — ограничивать ребёнка высотой, которую он же задаёт, это круг. У контейнера верхнего уровня владельца нет, и он не ограничен.

Три правила:

- ограничивается **только та ось, которую тянут** — иначе перетаскивание одного края задним числом ужимало бы уже вылезший контрол по другой;
- ограничение применяется **до** `Min`/`Max`, чтобы минимум побеждал и контрол не схлопывался у края формы;
- **у группы ограничивается рамка целиком**, как и при привязке к сетке.

`CoerceTargetSize` читает `MinWidth`/`MaxWidth`/`MinHeight`/`MaxHeight`, которых редактор раньше не видел вовсе: он писал 429 там, где раскладка выдавала 60, и дальше считал от несуществующей величины. Порядок как в Avalonia — сначала максимум, потом минимум, поэтому при конфликте побеждает минимум.

`InteractionOptions.ResizeMinSize` при этом до шва **не доходит**. Это ограничение жеста — «мышью мельче не сделать», — а не свойство контрола, и разница видна ровно на элементе, который уже мельче порога. Стоя на шве, минимум применялся к **каждой** записи размера, а `ItemResizingState.Enter` записывает текущий размер, чтобы от него считать: одно нажатие на ручку, ещё без движения, раздувало `TextBlock` 50×16 до 50×20 при пороге 20. Тем же путём он проходил через `ApplyGeometry`, то есть отмена возвращала не то, что было. Порог теперь считается на входе в жест и **никогда не увеличивает**: `max(min(ResizeMinSize, начальный размер), MinWidth/MinHeight контрола)`. Элемент в 16 пикселей при пороге 20 остаётся шестнадцатью и мельче не становится; элемент в 40 по-прежнему упирается в 20.

Отсюда следствие для хоста: порог **запрещает уменьшать**, а не задаёт «нормальный» размер. Демо держит его равным умолчанию библиотеки (10) — прежняя двадцатка не давала тронуть высоту почти у всей типографики макета, где строки 13–16 пикселей.

### Привязка к сетке

Включена по умолчанию — иначе сетка остаётся декорацией. Точка входа одна: `ShouldSnap` / `ResolveSnapStep` / `SnapCoordinate` / `SnapPosition` в `UiDesignerView`.

Шаг берётся у `PART_Grid.CellSize`, если `InteractionOptions.SnapStep` равен `NaN` (значение по умолчанию). Это не «удобство», а страховка: иначе редактор мог бы рисовать одну структуру, а привязывать к другой. Явный шаг перекрывает сетку. Нет шаблона — нет сетки — `ResolveSnapStep()` возвращает 0 и `ShouldSnap` даёт `false`; поэтому `GroupResizeOperationTests` с голым `new UiDesignerView()` продолжают проверять чистую арифметику.

Три правила, каждое закрыто тестом:

- **Привязывается результат, а не дельта.** `SnapPosition(_elementStartLocation + appliedTotalDelta, ...)`. Округление дельты сохранило бы исходный сдвиг элемента относительно сетки, и на узел он бы никогда не встал.
- **При resize привязывается двигающийся край**, а не размер, и **до** клампа по минимуму. Порядок важен: сначала край на узел, потом ограничение размера — иначе кламп сбивал бы уже привязанное значение.
- **У группы привязывается рамка целиком**, а не каждый target. `GroupResizeOperation.SnapBounds` работает с `nextBounds` до вычисления `scaleX`/`scaleY`; привязка каждого target'а по отдельности стянула бы соседей к общим узлам.

Групповое перетаскивание получает уже привязанное смещение (`effectiveDelta = snapped - _elementStartLocation`), поэтому взаимное расположение внутри группы сохраняется.

Притягивается при этом **рамка выделения**, а не тот элемент, за который группу схватили. Так уже устроен групповой resize, и так же выглядит происходящее на экране: пользователь видит рамку и ведёт её. Рамка снимается один раз на входе в жест (`GroupDragOperation.Frame`), а `FrameOffset` переводит её положение в положение источника и обратно.

Отображение стоит **снаружи** всего разрешения, а не внутри ветки направляющих: правило одно на всю привязку, и на узел сетки обязана садиться та же рамка. Первая версия правки этого не учла — при выключенных направляющих ранний выход обходил рамку, и сетка по-прежнему привязывала схваченный элемент.

Интервалы для группы из этого следуют сами: раз разрешается рамка, зазоры считаются для неё, и группа встаёт между соседями как один элемент. Отдельной ветки под неё нет.

`SnapCoordinate` считает через `Math.Floor(value / step + 0.5) * step`, а **не** `Math.Round`. `Math.Round` округляет к чётному, поэтому ровно посередине между узлами направление зависело бы от чётности узла (310 → 320, но 290 → 280) и край дёргался бы назад при медленной протяжке.

Resize читает модификатор из `editor.LastInputModifiers`: в `ResizeDeltaEventArgs` модификаторов нет.

Нюдж стрелками привязку **не** использует сознательно: она исправляет неточный ввод указателем, а клавиатура задаёт смещение точно. Иначе `NudgeStep` меньше шага сетки перестал бы работать вовсе.

Координаты поверхности вложенного контрола считаются относительно `UiDesignerPanel` (см. `TryGetTargetBounds`), то есть совпадают с мировыми. Поэтому вложенный ребёнок садится на ту же глобальную сетку, которую видно на фоне, даже если его контейнер стоит мимо узлов — конвертация координат для привязки не нужна.

### Направляющие выравнивания

Включены по умолчанию — по той же причине, что и привязка к сетке. Арифметика вынесена в `Guides/SurfaceSnapGuideResolver` и не знает ни визуального дерева, ни редактора: соседи приходят готовыми прямоугольниками в мировых координатах, поэтому правило одинаково работает и для вложенного контрола, и для контейнера верхнего уровня.

Кандидатов по каждой оси три — ближний край, центр, дальний край, — и сравнивается каждый с каждым. Выравнивание «правый край к левому краю соседа» получается из этого само, отдельного правила под него не нужно. Побеждает наименьшее по модулю смещение; при равенстве остаётся найденный раньше, а порядок перебора фиксирован, поэтому результат не зависит от порядка соседей в списке.

Четыре правила, каждое закрыто тестом:

- **Оси независимы.** Направляющая занимает свою ось, сетка получает остальные: элемент может встать на край соседа по X и на узел сетки по Y. Композиция та же, что и везде в редакторе, — `ResolveDragPosition` собирает результат по осям, а не целиком.
- **Направляющая сильнее сетки** на той оси, которую заняла. Сетка задаёт регулярность, направляющая — отношение к конкретному соседу, и оно точнее. Обратный порядок сбивал бы уже найденное выравнивание.
- **Соседи снимаются один раз**, на входе в жест (`BeginSnapGuides`). Это не оптимизация: во время жеста они не двигаются, а вот layout-проход внутри жеста мог бы сдвинуть те самые линии, в которые пользователь целится.
- **Из соседей исключается всё, что едет вместе с жестом** — сам target, остальное выделение при групповом перетаскивании и их родня по дереву. Иначе элемент выравнивался бы сам по себе и линия висела бы на нём всю протяжку.

Соседями считается то же, что редактор разрешает выбрать (`IsSelectableTarget`): правило одно, и выровняться можно ровно по тому, что видно как отдельный элемент. К ним добавляются границы самой формы — по её краям и центру выравнивают чаще всего, а отдельным элементом она не является. При перетаскивании контейнера верхнего уровня соседи — остальные контейнеры.

`SnapGuideTolerance` задан в **пикселях экрана** и делится на `ViewportZoom`. В мировых единицах на отдалении направляющая хватала бы элемент с расстояния, на котором его не видно.

Вид выравнивания линия несёт сама (`SurfaceSnapGuide.Kind`), и нужен он ровно для оформления: центр к центру принято показывать иначе, чем край. Центральной линия считается, только когда центры совпали **с обеих сторон** — совпадение центра с чужим краем это всё ещё выравнивание по краю, симметрии в нём нет. Отсюда же следует, что перебор выравниваний соседа нельзя обрывать на первом совпавшем: у прямоугольника нулевой толщины — а это пользовательская направляющая — край и центр совпадают, и выход по первому навсегда прятал бы центр. Накопление границ линии при этом идемпотентно, повтор ничего не портит.

Линии публикуются через `SnapGuides` с той же дисциплиной, что и выделение: набор сравнивается с текущим, и совпадающий не публикуется вовсе. Метод вызывается на каждом кадре протяжки, а линии меняются редко.

`SnapBypassModifiers` отключает привязку целиком — и к сетке, и к направляющим. Обещание одно: «держу нажатым — ставлю куда хочу», и делить его между двумя видами привязки было бы нечестно.

Resize пользуется тем же резолвером, но входит в него иначе. При перетаскивании снимается позиция и у элемента три кандидата на ось; при resize пользователь тянет **конкретный край**, и кандидат один — сам этот край. Отсюда отдельная точка входа `TryResolveEdge` и `ResolveResizeEdge` на редакторе. У соседа кандидатов по-прежнему три, поэтому потянутая сторона садится и на край соседа, и на его центральную ось.

Порядок внутри resize не изменился: направляющая занимает ось, сетка получает остальное, и только потом идут ограничение по форме и `Min`/`Max`. Линии публикуются по **применённой** геометрии: край мог упереться в минимум или в границу формы, и показывать выравнивание, которого не случилось, нельзя.

Правило «дельты resize накапливать нельзя» здесь ничего не ломает, и это проверено замером, а не рассуждением: `Resize_Across_A_Guide_Does_Not_Oscillate` протягивает край через линию тридцатью шагами и требует монотонной ширины. Остаток, съеденный направляющей, поглощается тем же способом, что и остаток от сетки, — состояние считает от применённой геометрии и запоминает применённое.

У группы направляющая ловит рамку выделения целиком, как и привязка к сетке: `GroupResizeOperation.SnapBounds` работает с `nextBounds` до вычисления масштаба.

### Равные интервалы

`SurfaceSpacingResolver` ставит элемент так, чтобы зазоры вокруг него стали равны, и показывает их отрезками с засечками. Равенство достигается двумя разными способами, и оба нужны:

- **Посередине** — зазоры до ближайших соседей слева и справа равны друг другу. Требует соседей с обеих сторон.
- **Повтор шага** — зазор до ближайшего соседа равен тому, который уже стоит между двумя соседями дальше по ряду. Так элемент продолжает существующий ритм, и это единственное, что работает в конце ряда, где с одной стороны никого нет.

Кандидатов на ось поэтому несколько, и побеждает ближайший — то же правило, что и у выравнивания. Иначе выбор зависел бы от порядка проверок, а не от того, куда человек ведёт элемент.

Подсказка показывает не «зазор рядом с элементом», а **цепочку равных зазоров**, в которую он попал: два подряд при положении посередине, два и больше при повторе шага. Одинокий зазор ничего не сообщает и не рисуется, а равенство где-то в стороне от элемента к нему не относится — цепочка ищется от прилегающих к нему зазоров. Арифметика вынесена туда же, куда и выравнивание, и по той же причине: соседи приходят готовыми прямоугольниками, редактора и дерева резолвер не знает.

Отличие от выравнивания в том, что сравниваются **зазоры**, а не координаты, и отсюда два требования, которых у выравнивания нет:

- **Сосед должен лежать в одном ряду** — перекрываться с элементом по другой оси. «Слева» и «справа» осмысленны внутри ряда, а коробка этажом выше стоит слева по координате, но интервала с ней не образует.
- **Сосед с нулевой площадью не считается.** Пользовательская направляющая приходит именно таким прямоугольником, а интервал бывает между элементами, а не до линии.

Порядок: **выравнивание → интервал → сетка**. Выравнивание точнее — оно связывает элемент с конкретным краем соседа, а интервал с расстоянием, которого на макете не видно; сетка забирает то, на что не нашлось отношения. Ось занимается независимо, как и везде.

Считается это только когда хотя бы одна ось свободна: при обеих занятых выравниванием интервалы не вычисляются вовсе. Мелочь, но она дважды сделала тест на приоритет бессмысленным — он проходил, ничего не проверяя, потому что до сравнения дело не доходило (см. комментарии в `EqualSpacingTests`).

Подсказка рисуется отрезком с засечками, а не линией через холст: линия читается как «здесь проходит ось», а измерение зазора — как «вот столько». Кисть своя, `Surface.SpacingBrush`. Выключается через `InteractionOptions.IsEqualSpacingEnabled`.

При изменении размера работает то же правило, но вход другой, и это та же разница, что и у направляющих. При перетаскивании элемент целиком встаёт посередине, и оба зазора считаются заново; при resize неподвижный край остаётся на месте, значит его зазор **задан**, и вопрос один — где должен встать двигающийся край, чтобы второй зазор стал таким же. Отсюда `TryResolveEdge` рядом с `TryResolveOffset`.

Ради равенства элемент не схлопывается: если ровное значение края переходит через неподвижный, запрос отклоняется. Проверять это нужно стендом, где отказ даёт именно это правило, а не радиус захвата, — иначе тест ничего не показывает.

### Распределение поровну

`DistributeHorizontally` / `DistributeVertically` — операция над выделением, а не подсказка внутри жеста: она выполняется целиком и одной единицей редактирования, поэтому отмена возвращает весь ряд, а не по элементу.

Равными делаются **зазоры**, а не расстояния между центрами. Тем же словарём описан весь остальной интервал в библиотеке, и при разной ширине элементов это разные ответы: ровные центры выглядят неровно именно потому, что зазоры при них разные.

Крайние элементы задают отрезок и остаются на месте, поэтому их политика перемещения роли не играет. А вот заблокированный **промежуточный** отменяет операцию целиком: расставить остальных значило бы выдать за распределение то, что им не является — зазоры равными всё равно не станут. То же правило, по которому смешанная группа locked/unlocked не двигается вовсе.

Меньше трёх элементов распределять нечего: два уже задают отрезок и никуда не двигаются.

### Пользовательские направляющие

`UiDesignerView.Guides` — набор линий, заданных снаружи. От направляющих выравнивания они отличаются происхождением и сроком жизни: те редактор находит сам и показывает только внутри жеста, эти задаёт хост, и они видны всегда.

Притяжение при этом **общее**, и отдельной ветки под них нет. Направляющая приходит в резолвер прямоугольником нулевой толщины: у него ближний край, центр и дальний край совпадают, и правило «каждый кандидат с каждым» само сводится к одному сравнению. Отсюда бесплатно берутся и композиция осей, и «направляющая сильнее сетки», и обход по `SnapBypassModifiers` — они записаны один раз для всех соседей.

Три вещи, каждая закрыта тестом:

- **Набором владеет хост.** Редактор его читает и показывает, но не создаёт и не удаляет записи — как и с деревом контролов. Коллекция с `INotifyCollectionChanged` отслеживается: добавленная линия действует сразу, без переприсваивания свойства.
- **Снимок сравнивается с текущим**, и совпавший не публикуется. Та же дисциплина, что у выделения и у линий выравнивания: иначе переприсваивание эквивалентной коллекции инвалидировало бы привязку слоя.
- **Линия рисуется через весь viewport**, а не отрезком. Направляющая задаёт координату, а не отношение двух элементов, и обрывать её незачем — в отличие от линии выравнивания, по длине которой видно, к чему идёт совпадение.

Кисть отдельная (`Surface.UserGuideBrush`, своя для Light и Dark), толщина общая с линиями выравнивания. Штрих раздельный, и умолчания разные не по вкусу: линии выравнивания пунктирные, потому что живут только внутри жеста и обязаны читаться как подсказка, пользовательские сплошные, потому что поставлены человеком и остаются на макете.

`ShowGuides` прячет линии, не трогая набор: `Guides` остаётся как был, и включение возвращает всё на место. Спрятанную линию нельзя ни подвинуть, ни вытянуть новую с линейки — жест по невидимому объекту читается как самопроизвольное поведение редактора. **Притяжение к ней при этом продолжает работать**, ровно как у сетки, которую `ShowGrid` тоже только прячет; выключается оно отдельно, через `InteractionOptions.IsSnapToGuidesEnabled`.

Перемещение и удаление направляющей указателем устроены как перестановка среди соседей и по той же причине: во время протяжки редактор ничего не меняет, а рисует превью, и один раз просит на отпускании через `GuideChangeRequested`. Уведённая за пределы редактора линия убирается — это тот же жест в обратную сторону, и другого способа не нужно. Без подписчика жест не начинается вовсе.

**Линейка стоит рядом с редактором, а не в его шаблоне.** `SurfaceRuler` — публичный контрол, который хост ставит сам; ему достаточно задать `Editor`, масштаб и положение он берёт оттуда. Внутрь шаблона линейку класть нельзя: у редактора точка ввода совпадает с точкой viewport'а, и слой, занявший место сверху или слева, сдвинул бы это соответствие вместе со всеми тремя системами координат. Горизонтальная линейка порождает горизонтальные направляющие, вертикальная — вертикальные; отпускание мимо холста не создаёт ничего, потому что тем же жестом линию убирают.

Выключателей два, и они не дублируют друг друга. `UiDesignerView.ShowRulers` гасит обе линейки разом: линейка следит за ним у своего `Editor` так же, как за масштабом, и ставит себе `IsVisible` через `SetCurrentValue` — привязка хоста к этому свойству переживает переключение. `SurfaceRuler.IsScaleVisible` убирает только деления и подписи, оставляя полосу, с которой по-прежнему вытягиваются направляющие: «шкала мешает читать макет» и «линейка не нужна вовсе» — разные требования.

Шаг шкалы берётся из ряда 1-2-5 на степенях десяти — только такие числа читаются как круглые на любом масштабе. Крупное деление определяется по номеру шага, а не сравнением остатка: накопление координаты уводит остаток от нуля, и подписи начинали бы пропадать тем чаще, чем дальше уехал viewport.

**Нажатие на направляющую перехватывается в фазе туннелирования.** Линия нарисована поверх всего, значит и жест должна забирать раньше контейнера под ней, а через всплытие это недостижимо: контейнер обработает нажатие первым, захватит указатель и начнёт своё перетаскивание. Обработчик написан так, чтобы вне попадания в линию его влияние было ровно нулевым, и это закреплено отдельным тестом — не только «направляющая выигрывает», но и «мимо неё выбор работает как раньше».

### Замена слоя направляющих

Слой ставится **рядом** с редактором, а не вместо части его шаблона, и это то же решение, что у линейки. Свой шаблон редактору написать всё равно нельзя: он называет `UiDesignerPanel`, `SelectionAdornerLayer` и конвертеры, которые остаются internal. А поверх редактора хост кладёт что угодно сам.

Отсюда состав опубликованного: данные (`SnapGuides`, `SpacingHints`, `UserGuides`, `GuidePreview`), модель линии (`SurfaceSnapGuide`, её ориентация и вид, `SurfaceSpacingHint`) и сам `SnapGuideLayer`. Резолверы остались internal — считать заново хосту незачем, а форма у них меняется с каждым новым правилом; сторожит `Guide_Arithmetic_Is_Not_Public`.

Слою снаружи достаточно задать `Editor`: положение, масштаб и все четыре набора он берёт оттуда через `PropertyMirror`. Шесть отдельных привязок обязаны были бы совпадать между собой, и рассинхронить их проще, чем заметить.

**Данные переносятся, выключатели показа — нет.** `ShowGuides` и `ShowSnapGuides` существуют, чтобы погасить встроенный слой; подхватывай их слой хоста, тот гасил бы вместе с чужим и свой, и заменять отрисовку было бы нечем. Дефект был именно такой — его нашла мутация, а не рассуждение.

Оба выключателя прячут, но не отменяют: притяжение к направляющим и интервалы продолжают работать, как сетка при выключенном `ShowGrid`.

### Миникарта

`SurfaceMinimap` — инструмент любой поверхности (ADR 0005): дизайнера интерфейса, редактора узлов, голого
`SurfaceView`. Хост ставит её рядом с редактором или поверх него, как линейку, и задаёт `Editor`;
остальное она берёт у редактора сама — контейнеры верхнего уровня (`ContainerFromIndex`), видимую
область, масштаб. Что нарисовать сверх контейнеров, слой выше отдаёт через internal-шов
`IMinimapLayer`, найденный службой редактора (`GetService`), — так редактор узлов дорисовывает связи.

Показывает она **объединение занятого и видимого** с полем в 5 % большей стороны, в одном масштабе по
обеим осям: рамка видимой области всегда на карте. Отсюда поведение, которое легко принять за
дефект: щелчок в пустоту за краем занятого уводит холст туда, карта раздвигается, и повторный щелчок
в ту же точку уводит дальше. Внутри занятого повторный щелчок холст не двигает — рамка уже там.

Щелчок мимо рамки ставит туда центр холста; взятую рамку ведут без скачка — запоминается смещение
захвата, а не центр. Пока тянут, соответствие карты стоит: рамка — часть показанного, и иначе карта
ехала бы под указателем. Держит это тест с кадрами между движениями — без кадров карта не
пересчитывается, и заморозку нечем было бы проверить.

Содержимое — прямоугольники контейнеров и кривые слоя выше — карта собирает снимком в мировых
координатах (ADR 0007) и отдаёт двум своим частям (ADR 0011): `MinimapContent` рисует снимок своей
операцией (`ICustomDrawOperation`, границы — прямоугольник карты) под кэшем в картинку (`BitmapCache`),
`MinimapFrame` — рамку видимой области поверх. Смена viewport — подпиской на его свойства, прохода
раскладки она не вызывает, — двигает одну рамку; содержимое записывается заново, только если сменились
снимок, соответствие карты или кисти. Геометрией содержимое больше не рисуется: композитор меряет
границы каждой новой записи геометрии — точные границы пути и путь обводки ради пера, — и на
10 000 узлах это стоило около 16 мс кадра на любом масштабе. Пересчёт карты идёт **кадром анимации**
(`RequestAnimationFrame`), а не в `Render`: он отдаёт новое частям, те просят перерисовки, а внутри
прохода отрисовки Avalonia её просить не даёт — бросает «Visual was invalidated during the render
pass». Пересобирает содержимое сигнал
поверхности `ContentChanged`: контейнер сменил границы или видимость, изменилась коллекция, слой выше
сообщил о своём (пересчёт концов связи, уход связи). Проход раскладки окна карта не слушает: событие
раскладки у Avalonia общее на окно, и прежде карта перерисовывалась от чужой раскладки. Во время
непрерывных правок пересборка — не чаще раза в `RebuildInterval` (50 мс): первая правка после тихого
интервала собирается на ближайшем кадре, следующие ждут таймера, и до него карта не перерисовывается —
без пересборки она показала бы то же самое. Другой редактор собирается сразу.

Перекрытие двух контейнеров закрашено, а не вырезано: каждый прямоугольник заливается сам
(`FillRectangle`), правила заливки у операции нет. Кривая рисуется ломаной, отрезков — по её длине на
карте (`Polyline`, 1…16), и кривая короче пикселя не рисуется вовсе.

В безголовых тестах таймер не срабатывает, а настоящие часы идут, и прореживание зависело бы от
скорости машины. Поэтому тесты ставят карте стоящие часы (`MinimapClock`, до первой отрисовки),
переводят их на интервал, когда правка должна собраться сразу, и дособирают отложенное
`FlushContent` — тем же, что зовёт таймер.

Ловушка стенда: геометрию в безголовом режиме собирает заглушка платформы, у которой конец каждой
фигуры пересчитывает рамку по всем уже добавленным точкам, — сборка из N фигур стоит там O(N²), около
60 мс на 2000 узлах. На Skia та же сборка линейна: 0,57 мс на 2000 прямоугольников и 2,5 мс на 10 000,
кривые — 0,36 и 1,4 мс (консольная проба на `UseSkia` с `UseHeadlessDrawing = false`). Число
пересборки со стенда для решений не годится; перерисовка — годится.

Снятая с дерева карта отписывается и останавливает таймер: редактор живёт дольше и держал бы её, а
назначенный таймер лежит у диспетчера. Это проверяют тесты со сборкой мусора и контрольной картой,
оставшейся на месте.

### Границы ответственности

`ArxisStudio.Surface` и `ArxisStudio.Markup` — две самостоятельные библиотеки со своими API. Деревом контролов владеет вторая.

Редактор **читает** дерево — без этого он ничего не покажет, — но не создаёт, не удаляет и не переставляет. Структурные намерения он выражает запросами: `DeleteRequested`, `ReorderRequested`. Пока обработчик не выставил `Handled`, ничего не происходит.

Проверять границу можно механически, но правило нужно формулировать точно — иначе оно ловит собственный chrome редактора. Мутации `Panel.Children` в `src/` есть, и все они законны:

```bash
grep -rn "Children\.\(Add\|Remove\|Insert\|Move\|Clear\)" src/ --include=*.cs
```

Законных попаданий пять видов, и все они сейчас в выдаче: `TransformGroup.Children` в конструкторе `UiDesignerView` — это трансформации viewport'а, к дереву контролов отношения не имеющие; `Children.Clear`/`Children.Add` в `SelectionAdornerLayer`, который сам является `Panel` и строит адорнеры выделения, — это оверлей редактора, а не редактируемая разметка; его же локальный список `desiredChildren`, который под шаблон запроса подходит по имени; одно упоминание `Children.Move` в XML-doc контракта; и `Children.Add` в `EnsureNode` (`UiDesignerView.Grouping.cs`) — это список вложенных групп у построителя `SurfaceGroupInfo`, ответ на запрос `GetGroups`, а не панель. Всё остальное — нарушение.

Первая версия этой проверки была написана с точкой перед `Children` и потому не видела неквалифицированных вызовов внутри самого `SelectionAdornerLayer`; заодно она утверждала, что все `Children.Add` живут в `UpdateTransforms`, хотя четыре из них — в конструкторе. Исправленная версия прогнана: выдача совпадает с пятью перечисленными видами, незаконных мутаций в `src/` нет. Пятый — дерево групп — появился вместе с вложенными группами, и список его не знал, пока проверку не прогнали снова.

Отсюда деление контракта изменений: `EditCompleted` описывает только то, чем распоряжается редактор — геометрию и `ZIndex`. Запись и отмена структурных правок принадлежат тому, кто их выполняет.

### События перетаскивания

`DragStarted` / `DragDelta` / `DragCompleted` — публичные routed-события контейнера, и у них есть неочевидная часть, на которой потребитель ошибётся первым делом.

`DragDelta` несёт **применённую** дельту за кадр: уже после привязки к сетке, направляющих, ограничения по форме и политик перемещения. Не движение указателя. Совпадают они только когда ничто ничего не поправило. `DragCompleted` несёт накопленную применённую сумму, то есть ровно сумму всех `DragDelta`.

Отсюда практическое: заблокированная политикой ось в событиях не появляется вовсе — сдвига по ней не было. И при включённой привязке сумма дельт не равна тому, на сколько провели мышью.

`DragStarted` при этом несёт не смещение, а **точку нажатия** в координатах редактора, несмотря на имена свойств `HorizontalOffset`/`VerticalOffset`.

### Контракт изменений

Вся геометрия пишется ровно через два метода — `SetTargetPosition` и `SetTargetSize`. Это единственный шов, и держать его единственным важно: на нём стоит запись изменений для undo. Прямые присваивания `Location`/`Width`/`Height` остались только в fallback-ветках состояний, где редактора нет вообще.

`SurfaceEditScope` копит изменения в пределах жеста. Он записывает **задаваемые значения**, а не перечитывает состояние: иначе итог зависел бы от того, успел ли пройти layout к моменту фиксации. Исходное состояние снимается один раз, при первом обращении к target.

Границы жестов — четыре пары в `UiDesignerView`: `OnItemsDragStarted`/`OnItemsDragCompleted` и три пары resize (primary, secondary, group). `BeginEdit` вызывается **после** всех guard-проверок, но **до** первой мутации: `ItemResizingState.Enter` и `TryCreateGroupResizeOperation` фиксируют текущий размер, и это должно попасть в «до», а не потеряться.

`ApplyGeometry`, `ApplyOrder`, `Revert` и `Reapply` подавляют запись через `_suppressEditRecording` — иначе отмена порождала бы новую запись и стек никогда не пустел бы.

**Политики ограничивают жест, а не хоста.** `SetTargetGeometry` не спрашивает `SurfaceInteraction`: это правила **взаимодействия**, их читают точки жеста, а вызов API — просьба самого хоста, который пометку и поставил. Запрещать ему значило бы сделать заблокированный элемент неподвижным навсегда: отмена возвращает геометрию тем же семейством методов. Хосту, которому нужен запрет в интерфейсе, редактор сообщает политику сам (`PrimarySelectionMovePolicy`) — так и сделана панель свойств демо. Правило неочевидное и потому закреплено тестом.

**Правку геометрии снаружи жеста делает `SetTargetGeometry`.** Это тот же путь, что у перетаскивания: те же швы, та же единица редактирования, те же отсечки — раскладка вправе не отдать положение, а размер ограничивают `Min`/`Max` и границы формы. Без него у хоста не было способа изменить геометрию так, чтобы правка попала в `EditCompleted`: `ApplyGeometry` запись как раз подавляет, потому что им отмена и повтор возвращают уже записанное. Ответ («приняли или отсекли») берётся у контракта изменений, а не перечитыванием координат поверхности: те отстают на проход диспетчера и сразу после записи ещё старые — ради этого `CommitEdit` и стал возвращать признак.

**`Margin` и выравнивание — это геометрия другой дорогой, и она вне отмены.** Замер: запись `Margin` хостом сдвинула элемент со 110,110 на 140,130, а событий контракта не было ни одного. Границы это не нарушает — свойствами контрола распоряжается хост, — но отменить такой сдвиг нечем, и редактор о нём узнаёт только тем, что пересчитывает координаты поверхности из фактической раскладки.

Вид изменения для `ZIndex` называется `SurfaceEditKind.Order`, а не `Reorder`: словом «reorder» теперь называется перестановка среди детей панели, и одно имя на два разных действия уже путало — обработчик, написанный на «изменился порядок», молча ловил половину случаев.

Порядок перекрытия идёт тем же путём: `SetTargetZIndex` — третий и последний шов рядом с `SetTargetPosition`/`SetTargetSize`. `ZIndex` — свойство контрола, поэтому он остаётся за редактором; порядок среди детей панели — уже структура дерева, и швом не является вовсе (см. «Границы ответственности»). Изменения наследуют общий `TargetChange`, чтобы хост не разбирал типы.

Важное про тему: в `UiDesignerItem.axaml` **нельзя** возвращать `ZIndex` в стиль `:selected`. Раньше выбранный элемент поднимался на 99 ради своей рамки, но рамки давно на уровне редактора, а такой подъём молча перебивает порядок, заданный `BringToFront`/`SendToBack`. На это есть тест.

### Политики редактирования

`ArxisStudio.Surface.Editing.SurfaceInteraction` — `ResizePolicy` (флаги сторон) и `MovePolicy` (оси). Проверяются в `ApplyMovePolicy` / `IsResizeAllowed` и применяются одинаково к одиночному target, nested-группе и групповым операциям. Полностью заблокированный target (`None`/`None`) рисуется locked-визуалом, ручки становятся неинтерактивными.

### Конфигурация ввода

Жесты и числовые параметры не захардкожены, а вынесены в объекты-конфиги, доступные из AXAML/стилей/биндингов:

- `SurfaceInputGestures` — `PanButton/PanModifiers`, `MarqueeButton/MarqueeModifiers`, `ZoomModifiers`, `ContainerInteractionModifiers`, `AdditiveSelectionModifiers`, `LargeNudgeModifiers`, `KeyboardResizeModifiers`, `SnapBypassModifiers`
- `SurfaceInteractionOptions` — `ZoomStep`, `DragStartThreshold`, `ResizeMinSize`, `NudgeStep`, `LargeNudgeStep`, `IsSnapToGridEnabled`, `SnapStep`, `IsSnapToGuidesEnabled`, `SnapGuideTolerance`, `IsResizeContainedToParent`, `IsPinchZoomEnabled`, `IsAutoPanEnabled`, `AutoPanEdge`, `AutoPanSpeed`

Колесо помечается обработанным только тогда, когда зум действительно состоялся: `EditorState.OnPointerWheelChanged` возвращает признак, а `TryHandleZoom` отвечает `false`, если `ZoomModifiers` заданы и не нажаты. Безусловный `Handled` съедал колесо и в этом случае, и внешний `ScrollViewer`, внутри которого лежит редактор, переставал прокручиваться вовсе. На границе диапазона зума колесо всё равно считается потреблённым — жест был наш, и отдавать его наружу у края значило бы, что страница вдруг начинает ехать.

Все пути масштаба сходятся в `ZoomAt(zoom, origin)`: точка холста под `origin` остаётся на месте, масштаб ограничен `MinZoom`/`MaxZoom`. Путей три, и числа у них разного смысла — сверено с исходниками Avalonia 12, а не угадано (`SurfaceView.Pinch.cs`):

- **колесо** — шаг `ZoomStep` на щелчок; сюда же приходит щипок точного тачпада на Windows — как колесо с `Ctrl`;
- **щипок тачпада** (`PointerTouchPadGestureMagnifyEvent`, macOS) — в `Delta` **приращение за событие**, поэтому масштаб умножается на `1 + Δ`;
- **щипок пальцами** (`PinchGestureRecognizer`, только касание и перо) — `Scale` **накоплен от начала жеста**, поэтому считается от масштаба в начале щипка, а не от текущего: иначе два события 1,5 и 2 дали бы 3 вместо 2. Точка холста между пальцами в начале остаётся между ними весь жест, так что щипок заодно панорамирует.

Щипок модификаторов не спрашивает: `ZoomModifiers` отличают масштаб от прокрутки колесом, а щипок ни с чем не спутать. Выключается он `IsPinchZoomEnabled`, и выключенный события не забирает. Настоящего касания headless не умеет, поэтому `PinchZoomTests` поднимают события руками с теми аргументами, что даёт платформа. **На живом сенсорном экране щипок не проверялся:** распознаватель захватывает оба касания, когда ложится второй палец, и первый палец к этому моменту мог начать рамку — её закрывает потеря захвата, как любой брошенный жест, но что при этом успеет выбраться, покажет только живое касание.

**Автопрокрутка у края** (`SurfaceView.AutoPan.cs`) — у перетаскивания и рамки. Жест сообщает положение указателя на каждом движении (`TrackAutoPan`), и если оно в полосе `AutoPanEdge` у края или за ним, таймер сдвигает холст и пересчитывает жест **по той же точке экрана**: указатель стоит, а под ним уже другое место холста. Скорость растёт с глубиной в полосе до `AutoPanSpeed`, за краем наибольшая; оси независимы. Скорость и полоса — в пикселях экрана, поэтому на отдалении та же скорость проносит больше холста. Включается движением, а не нажатием: нажатие у самого края ещё ничего не тянет. Останавливается на выходе из полосы и на выходе из жеста — и на отпускании, и на потере захвата.

Работает это только потому, что жест помнит **начало на холсте, а не на экране**. Перетаскивание раньше считало смещение как `мир(текущая) − мир(начальная)`, пересчитывая начальную точку экрана по текущему viewport: пока холст стоит, это одно и то же, а стоит ему сдвинуться — начало «уезжает» вместе с ним, и элемент перестаёт идти за указателем. Этот дефект жил и без автопрокрутки — зум колесом посреди перетаскивания сдвигал форму из-под указателя, — и тест на него (`Wheel_Zoom_Mid_Drag_Keeps_The_Form_Under_The_Pointer`) падает на прежней формуле. Рамка устроена так изначально.

**Изменение размера** ручкой автопрокрутку тоже умеет, но входит в неё иначе. Ручка сообщает о движении, только пока движется указатель; у края он стоит, поэтому шаг автопрокрутки повторяет обработчик ручки сам (`TrackResizeAutoPan` в `UiDesignerView`) — для одиночной ручки, ручки кластера и рамки группы. Размер при этом берётся не из дельты, а из **снимка указателя на холсте**, и шаг обязан пересчитать этот снимок раньше, чем жест (`RefreshPointerSample`): снимок хранит точку холста, а под неподвижным указателем после сдвига уже другое место. Дельта, которую шаг подаёт в обработчик, — сдвиг холста; её видит событие `ResizeDelta` контейнера, и это честно: относительно холста указатель ушёл ровно на столько. Тест обязан подвести указатель к ручке **до** нажатия: без этого снимка на входе в жест нет, и жест всю дорогу считает по дельте ручки — путь, которым живая ручка почти не ходит, и на нём пересчёт снимка ничего не решает; первая версия теста так и прошла, не проверив главного. Останавливают автопрокрутку и завершение ручки, и потеря захвата — оба пути, намеренно.

В безголовом режиме время стоит, поэтому `AutoPanTests` делают шаг таймера сами (`StepAutoPan`). Живой мышью автопрокрутка не проверялась.

Решения о жестах принимать через `ShouldStartPan` / `ShouldStartMarquee` / `ShouldHandleZoom` / `ShouldUseContainerInteraction` / `ShouldUseAdditiveSelection` / `ShouldDeferPressToMarquee`, а не сравнением `KeyModifiers` на месте. Политику интерпретирует редактор — состояния контейнера её не читают, а спрашивают.

Область действия рамки (`MarqueeScope`) вычисляется из **текущего прямоугольника** на каждом шаге протяжки одним правилом `FindContainerForMarquee`, и то же правило применяется в `CommitSelection`. Ничего не латчится: латченный владелец приводил к тому, что рамка навсегда оставалась привязанной к контейнеру, где было нажатие, а её визуальный охват обещал выборку, которой не происходило. Латчится только **режим** (container-level), и делает это `EditorSelectingState` — жест не должен менять смысл посреди протяжки.

Решает режим **точка нажатия**, а не только модификатор: рамка, начатая на пустом холсте, набирает формы, начатая внутри формы — её содержимое. Снаружи контейнеров выбирать содержимое не за что, пользователь видит формы и обводит формы; `ShouldUseContainerMarquee` спрашивается один раз, на входе в жест. `ContainerInteractionModifiers` остаётся способом потребовать форм и изнутри формы.

Следствие, которое стоит знать: набрать вложенные контролы рамкой можно только начав её внутри формы, то есть с пустого места в ней. У формы, покрытой содержимым целиком, такого места нет — но это ограничение `ShouldDeferPressToMarquee`, а не нового правила.

Латчится ещё и **набор контейнеров**, но это не исключение из правила выше, а то же самое правило: владелец пересчитывается каждый кадр по текущему прямоугольнику, а вот список кандидатов снимается один раз на входе в жест (`BeginContainerSnapshot` / `EndContainerSnapshot`, зеркально `BeginSnapGuides`). Причина та же, что у соседей для направляющих: дерево, изменившееся посреди протяжки, развело бы охват рамки и то, к чему она применилась. Окно снимка накрывает и `CommitSelection` — он вызывается до выхода из состояния.

Второй эффект — цена. Обход `EnumerateContainersCore` спускается в поддерево каждого контейнера верхнего уровня, то есть стоит по размеру **всего макета**, а не по числу форм, и до снимка повторялся на каждом кадре. Стенд под это лежит в репозитории — `MarqueeCostProbeTests`: 500 контейнеров, формы из двух и из тридцати контролов. Он печатает свои числа при каждом прогоне (на машине разработки — 0,55 и 1,56 мс на разрешение владельца), а **утверждает отношения**, а не миллисекунды: обход дорожает вместе с макетом, и со снимком эта зависимость исчезает — форма из тридцати становится не дороже формы из двух. Абсолютные величины зависят от машины, и потолок по ним либо ничего не ловит, либо мигает.

Отпускать снимок надо **на выходе из состояния**, а не пересобирать на входе в следующее: разница видна только чтениям между жестами — например разрешению контекста, — и первая версия теста её не поймала, потому что проверяла второй рамкой.

`ShouldDeferPressToMarquee` разрешает конфликт жестов на пустой области контейнера. Механика передачи важна: контейнер, уступая жест, **не захватывает указатель и не ставит `Handled`**, поэтому нажатие всплывает до редактора обычным маршрутом и `EditorIdleState` запускает рамку по `!e.Handled`. Никакого проталкивания состояний между двумя машинами — они остаются независимыми.

`ContainerInteractionModifiers` и `AdditiveSelectionModifiers` продублированы плоскими свойствами на `UiDesignerView` ради совместимости. Значение у них одно: геттер читает у набора, поэтому разойтись по значению они не могут. А вот **уведомления** держатся на связке: редактор слушает набор и ретранслирует два своих свойства. Без неё настройка через сам набор — путь, который документация и рекомендует, — оставляла привязку к плоскому свойству со старым значением: значение верное, показано прежнее. Заметить это по чтению нельзя, поэтому закреплено тестами (`InputGestureBridgeTests`), и каждый случай проверяется на **обоих** свойствах: первая версия проверяла уведомления на одном, и ветку второго можно было удалить целиком, не уронив ни одного теста.

Подписка **слабая** — `WeakEvents.AvaloniaPropertyChanged` через объект-ретранслятор, а не обычный `+=`. Обычная кладёт делегат в сам набор, то есть набор начинает держать редактор; набор, общий на несколько редакторов — а именно так его раздаёт один `Setter` в стиле, и документация свойства этот путь прямо предлагает, — не отпускал бы ни одного из них никогда. Замерено: на обычной подписке пять редакторов из пяти переживали принудительную сборку, на слабой — ни одного. У теста на это есть контрольная половина со своим набором: без неё он проходил бы и в случае, когда сборка вообще ничего не собрала.

Плоский сеттер пишет **только в набор**: событие поднимает ретранслятор, уже после записи. Своё `SetAndRaise` там поднимало бы его раньше, и подписчик, перечитавший геттер вместо `NewValue`, получал бы прежнее значение — тот же дефект наоборот.

### Курсоры жестов

Курсор — единственное, чем редактор отвечает на жест до того, как что-то сдвинулось. Задаются они двумя разными способами, и деление не по вкусу:

- **У жеста своего элемента нет.** Перемещение, панорамирование, рамку, перестановку и перенос направляющей начинает сам редактор по политике ввода — наводить курсор не на что. Такие курсоры лежат в `SurfaceCursors` (`UiDesignerView.Cursors`), рядом с `SurfaceInputGestures` и `SurfaceInteractionOptions`.
- **У части элемент есть, и его видно.** Ручка изменения размера и линейка — курсор задаёт сама часть, как принято в Avalonia. Настраиваемым его делает **ресурс** (`Surface.SelectionAdorner.Cursor*`, `Surface.Ruler.Cursor*`): литерал внутри `ControlTemplate` снаружи не перекрывается ничем — это уже замерено на `PART_HoverBorder`, и ровно так восемь курсоров ручек и были неперекрываемыми.

| Жест | Свойство | Умолчание | Где ставится |
| --- | --- | --- | --- |
| перемещение | `Move` | `SizeAll` | `ItemDraggingState` |
| отказ | `Blocked` | `No` | `ItemIdleState.RefuseDrag` |
| панорамирование | `Pan` | `Hand` | `EditorPanningState` |
| рамка | `Marquee` | `Cross` | `EditorSelectingState` |
| перестановка | `Reorder` | `DragMove` | `ItemReorderingState` |
| направляющая | `GuideHorizontal` / `GuideVertical` | `SizeNorthSouth` / `SizeWestEast` | `EditorGuideDraggingState` |

Четыре правила, каждое закрыто тестом:

- **Курсор ставится тому, кто держит захват.** Состояния контейнера — контейнеру, состояния редактора — редактору. Во время захвата указатель считается находящимся над захватившим элементом, поэтому его курсор выигрывает у содержимого формы, задавшего свой собственный, и наследование `Cursor` тут ни при чём.
- **Возвращается прежнее значение, а не `Cursor.Default`.** Прежние две ветки писали на выходе `Default` и затирали курсор, заданный хостом; на этом стоял тест, то есть затирание было закреплено. Запись идёт через `SetCurrentValue`, поэтому привязка хоста переживает жест.
- **Повторное применение — no-op.** Курсор жеста ставится на каждом движении указателя, и без сравнения одна протяжка писала свойство **48 раз** — замерено на живом демо через `watch_element`. Та же дисциплина, что у снимка выделения.
- **Отказ живёт в `ItemIdleState`, а не в `ItemDraggingState`.** До состояния перетаскивания заблокированный элемент не доходит вовсе — его отсекают проверки политики и раскладки. Поставь курсор запрета в `ItemDraggingState` — и он не появился бы ни разу. Отказом считается и отсутствие подписчика на `ReorderRequested`: для пользователя это тот же случай, элемент не переставится.

Курсор запрета ждёт порога перетаскивания: до него жеста ещё нет, и мигать на каждом нажатии он не должен.

Значение `null` у любого свойства означает «библиотечный курсор жеста», а не «не менять» — тот же приём, что `SnapStep = NaN`. Здесь он обязателен: `PublicSurfaceTests` работает **без** headless-приложения, а слепок читает значения по умолчанию у `AvaloniaProperty`; курсор в умолчании потребовал бы платформенной фабрики на загрузке типа. Умолчания поэтому ленивые, а закреплены они через `Cursor.ToString()` — единственное, что `Cursor` о себе рассказывает.

Набор читается **на входе в жест**, поэтому подписки на него у редактора нет: менять курсор посреди протяжки значило бы описывать жест, который уже идёт.

### Контекстные действия

Запрос складывается в `BuildContextRequest`, и `Scope` считается по **самому** target'у под курсором, а не по его контейнеру: попадание внутрь текущей группы даёт `Selection`, только если в группе лежит именно этот target. `Ctrl + A` набирает контейнеры, поэтому клик по их ребёнку — это `NestedTarget`, а не `Selection`. Правило неочевидное, и тест на него есть.

**Правый клик переводит выделение, только когда щёлкнули мимо него.** Попал внутрь — выделение остаётся как есть: оно принадлежит пользователю, и меню относится к нему целиком. `RetargetSelectionForContext` проверял это лишь для индексного слоя, а слой target'ов переписывал всегда — и выбор схлопывался до кластера под курсором. Две выбранные группы превращались в одну ровно в тот момент, когда над ними вызывают меню, и «Группировать» становилось недоступным.

Остановить поток можно двумя способами, и они разные:

- `Cancel` у `ContextMenuRequesting` — «контекста не будет вовсе»: ни показа, ни `ContextMenuResolved`.
- `Handled` — «покажу сам»: презентер молчит, но `ContextMenuResolved` приходит и говорит, что контекст показан.

Оба закреплены тестами, потому что по именам их не различить.

Запрос от указателя асинхронный и ждать себя не даёт: обработчик нажатия обязан вернуться сразу. Поэтому новый запрос **отменяет** предыдущий — провайдер вправе ходить в свою модель, и два правых клика подряд иначе разрешали меню дважды, вторым показом поверх первого. Упавший провайдер пишет в лог Avalonia; публичного события об ошибке нет намеренно — контракт асинхронный, и свои исключения хост ловит сам.

### Темы

Единая точка входа — `avares://ArxisStudio.Surface.UiDesigner/Themes/UiDesignerTheme.axaml`; приложение подключает только её. Своя тема есть у каждой сборки, и агрегирующая собирает их снизу вверх: `Surface/Themes/SurfaceTheme.axaml` (фон, рамка, сетка), `Surface.Editing/Themes/EditingTheme.axaml` (адорнеры, направляющие, линейки), затем свои словари дизайнера интерфейса. Ключ несёт имя слоя, который его объявляет (ADR 0006): `Surface.*` — ядро и инструменты, `UiDesigner.*` и `UiDesignerItem.*` — дизайнер интерфейса, `NodeEditor.*` — редактор узлов, `SurfaceMinimap.*` — миникарта. Имя ключа — часть контракта темы: приложения переопределяют ключи, и переименование ключа ломает их так же, как переименование типа, — поэтому ключи меняют вместе с именами типов, а не по одному.

Постоянная рамка контейнера включается ресурсом `UiDesignerItem.OutlineOpacity` (по умолчанию `0` — только под курсором). Рамка оверлейная: `PART_HoverBorder` лежит в той же ячейке шаблона, что и содержимое, и не участвует в раскладке. `BorderThickness` для этой цели не годится — `Border` разворачивает ребёнка внутри штриха, и форма рисуется на два пикселя уже объявленной.

Свойство задано ресурсом, а не стилем приложения, потому что перекрыть значение, заданное атрибутом внутри `ControlTemplate`, стиль извне не может: замер показал, что `Style Selector="... /template/ Border#PART_HoverBorder"` из `Application.Styles` не применяется, тогда как вложенный стиль самой `ControlTheme` — применяется. Наводить свои правила на чужие template parts бесполезно; расширять шаблон нужно ресурсом.

Отступ ручки считается из её размера (`HandleMarginConverter`, `-HandleSize/2`), а не задан литералом. Ручка сидит на краю выделения, значит наружу торчит ровно половина; литерал `-4` был подобран под размер по умолчанию 8, и любой, кто пользовался задокументированной настройкой `Surface.SelectionAdorner.HandleSize`, получал съехавшие ручки — молча, заметно только глазами. Правило общее: если ресурс объявлен настраиваемым, ни одно производное от него число не может быть литералом в шаблоне.

Кисти определяются через `ThemeDictionaries`, поэтому Light/Dark различаются без дублирования `ControlTheme`. `SelectionAdorner` использует ресурсные ключи по ролям и состояниям (`Surface.SelectionAdorner.Primary*` / `Secondary*` / `Group*` / `Handle*` / `Locked*`), а роль задаётся свойством `SelectionAdorner.Role`. Кастомизация внешнего вида должна идти через ресурсы, а не копированием шаблонов.

## Редактор узлов

`ArxisStudio.Surface.Nodes` — четвёртый слой, рядом с дизайнером интерфейса (ADR 0004): `NodeEditor :
SurfaceView`, `Node : SurfaceItem`, порты и связи. Первый этап — «соединения целиком»: связи под
узлами, протяжка новой связи, выбор и удаление связей, отцепление конца, стенд стоимости и демо.
Второй — «излом, разрезание, миникарта» (ADR 0005): узел-перевалка, разрез отрезком, связи на
миникарте инструментов. Третий — «раскладка и виртуализация» (ADR 0007): раскладка по изменениям,
контейнеры только у видимых узлов, записи связей и закешированная миникарта. Четвёртый — «малый
масштаб» (ADR 0008): ниже 50 % узлы — карточки с полосой заголовка, связи без контролов рисует
`SimplifiedLinkLayer`, нажатие по карточке разворачивает узел. Следом — оформление узла (ADR 0009):
заголовок стал частью узла, полоса видна в обоих видах, цвет провода берётся из модели, а базовый вид
рисуют темы, и хост меняет его по частям. Пятый — «выбор без контейнеров» (ADR 0010): выбранный узел
за окном свёрнут и остаётся выбранным, а правка идёт через модель.

Тема — `avares://ArxisStudio.Surface.Nodes/Themes/ArxisStudioNodeEditorTheme.axaml`: ядро,
инструменты и сам редактор, ключи `NodeEditor.*`.

**Оформление узла — базовое у библиотеки, а заменяет его хост по частям** (ADR 0009). Тема `Node`
рисует карточку и область заголовка: полоса — `SurfaceItem.Accent` из `ItemAccentBinding` ядра, название —
`Node.Header` из `ItemHeaderBinding`, область видна при любом из двух (`:header`). Цвет названия на
полосе выбирает узел — `:light-accent` по яркости сплошной кисти, порог WCAG 0,179, — и контраст держится
только вместе с цветами темы, белым и чёрным: тёмно-серое название давало 3,7:1, и это держит
`NodeHeaderTests.The_Title_Reads_On_Any_Band` проходом куба RGB. Цвет провода — кисть записи связи из
`LinkStrokeBinding` (`LinkRecord.Stroke`): контрол `Link` рисует ею обычное состояние
(`EffectiveStroke`), выбор, наведение и разрез — пером темы, а слой упрощённых связей группирует кривые
по кисти. Упрощённая карточка — копия узла: высоту полосы тема редактора берёт у
`NodeEditor.Node.HeaderHeight`, поэтому заголовок выше неё карточка не повторяет.

**Связь — запись, контрол — её вид** (`NodeEditor.LinkRecords.cs`, ADR 0007). Запись (`LinkRecord`)
есть у каждого элемента `Links`: ключи концов — из `LinkSourceBinding`/`LinkTargetBinding`, прочитанных
без контрола (`ObjectBindingReader`) и перечитанных по `INotifyPropertyChanged` модели; кривая, рамка,
выбор, подсветка, разрез, отцепление. Смежность «ключ → связи», попадание, разрез, выбор и миникарта
идут по записям. Контрол `Link` ставит на `LinkPanel` сам редактор, на мере панели: без виртуализации —
всем, с ней — видимым с запасом узлов и под курсором, разрезом или отцеплением; свёрнутый контрол
уходит в пул. Готовая `Link` из коллекции сама себе контрол и развёрнута всегда, а её концы хост меняет
на ней, и она сообщает редактору сама. У контрола, созданного редактором, `Source`/`Target` — вид
записи: писать в них мимо модели бесполезно. `ItemsControl` для связей больше нет — генератор
контейнеров здесь ничего не давал, а индекс связи никому не нужен.

**Связь знает концы данными портов.** Узлы — `ItemsSource`, связи — `Links`; концы каждой — ключи
портов, привязками `LinkSourceBinding`/`LinkTargetBinding` (приём `DisplayMemberBinding`). Ключ порта
— `Port.Data`, а без него `DataContext`; реестр держит порты по ключу и снимает только тот же
экземпляр — пересозданный контейнер регистрирует новый порт раньше, чем уходит старый. Конец связи —
центр `PART_Pin` порта в мировых координатах: положение узла плюс положение штырька в узле.

**Конец без живого порта** (`NodeEditor.LinkEnds.cs`, ADR 0007) — у свёрнутого при виртуализации
узла: положение узла из панели плюс смещение штырька, снятое при последнем показе (`_lastOffsets`,
только у виртуализирующей панели — обычная ищет индекс узла проходом по детям); у ни разу не
показанного — середина правого края для источника и левого для цели, если `PortNodeBinding` называет
узел по данным порта. Узел без контейнера о своём сдвиге говорит только панели, а она — поверхности
(`ItemGeometryChanged`: элемент — его связи, `null` — все, после перечитывания геометрии): связь,
созданная раньше, чем панель прочла геометрию, иначе так и осталась бы без концов. Ушедший из
коллекции свёрнутым узел уносит свои связи тем же сигналом. Сброс `Port.LastOffset` при смене ключа,
записанный в плане этапа, не понадобился: регистрация порта под новым ключом сама пересчитывает его
связи.

**Пересчитывается только то, что сдвинулось.** Сдвиг узла переносит концы его связей сразу, по
смежности «ключ → связи», поэтому кадр перетаскивания стоит степень узла — это счётчик `LinkUpdates`
и тесты `A_Drag_Frame_*`. Положение порта внутри узла сверяется **в конце раскладки узла**
(`Node.ArrangeOverride` → `OnNodeArranged`): только там поддерево узла разложено окончательно. На
границах самого порта его предки внутри узла ещё без своих — Avalonia ставит родителю границы после
того, как разложила детей, — и конец, посчитанный в этот миг, ложился мимо: связи во все входы узла
сходились у его левого верхнего угла. Нашла это живая проверка демо, а не тесты: у стенда порты
лежат прямо в панели узла, и узлы ставятся после первой раскладки. Держит `NestedPortTests`. Не
видна только перестановка, которая заново раскладывает элемент между портом и узлом, не трогая ни
того, ни другого.

**Попадание по связи считает редактор**, слой связей в попадании не участвует: нажатие, которое не
взял ни один узел, сравнивается с кривыми с допуском `LinkHitTolerance` в пикселях экрана. Сперва
отсев по рамке, которую связь держит сама (`WorldBounds`, уже с толщиной линии), и точное расстояние
— только у прошедших (`LinkDistanceChecks`). Подсветка наведения и нажатие спрашивают одно правило:
подсвеченное обязано быть тем, что выберет щелчок, и над узлом не отвечает ни то, ни другое —
движение узел не обрабатывает никогда.

**Структуру графа правит хост** (ADR 0001): `ConnectRequested`, `ReconnectRequested`,
`LinkDeleteRequested` — запросы с `Handled`, обход подписчиков останавливается на первом
выполнившем. Правила графа — хоста, в `ConnectValidating`; он спрашивается и о новой связи, и об
отцеплённом конце и называет перецепляемую связь (`Link`) — иначе «во вход — одна связь» отказало
бы связи, переносящей свой выход. Источник — всегда выход, в какую сторону ни тянули. Порт ловит
протягиваемый конец в радиусе `PortCaptureRadius` пикселей экрана и притягивает его к штырьку.

**Отцепляют протяжкой тела связи**: уходит ближний к нажатию конец (по параметру кривой — она
симметрична, и 0,5 делит её пополам и по длине). На другой порт того же направления — перецепить,
в пустоту — удалить, на свой — ничего; свой порт принимает конец без вопроса к хосту. Порт, отказавший
концу, пустотой не считается. Нажатие отдаёт захват протяжке как есть: снятый посреди жеста, он
объявил бы жест брошенным.

**Выбор связей отдельный от выбора узлов и взаимоисключающий**, поэтому Delete значит одно: команды
`nodes.cancelLink`, `nodes.clearLinkSelection` и `nodes.deleteLinks` стоят в наборе впереди встроенных
и уступают клавишу, когда им нечего делать.

**Направляющих выравнивания у редактора узлов нет по умолчанию.** Службу привязки он берёт у
инструментов ради сетки, а выравнивание по соседям и равные интервалы выключает в конструкторе
(`InteractionOptions`): узлы графа по краям соседей не ставят, и пунктир через холст на каждом
перетаскивании только мешал. Стенд `NodeStand` направляющих не трогает, чтобы тесты видели умолчание;
держит его `NodeEditorTests.A_Dragged_Node_Is_Not_Pulled_To_Its_Neighbour`.

**Положение узла — из модели**, привязкой ядра `ItemLocationBinding` (ADR 0007). `Location`
двусторонний по умолчанию, а ядро пишет его через `SetCurrentValue`: привязка хоста — локальная или из
стиля — переживает жест. Прежде запись была локальным значением, и привязка из стиля, которой
пользуются `FormsDesigner` и демо дизайнера интерфейса, после первого же жеста переставала двигать
контейнер: модель менялась, а контейнер стоял. Демо узлов держит положение в модели этой привязкой, с
`PortNodeBinding` и предполагаемым размером, — сказано в его `CLAUDE.md`.

**Излом — узел-перевалка, а не точка на связи** (ADR 0005). Связь в библиотеке остаётся одной
кубической кривой от порта к порту. Двойной щелчок по связи поднимает `LinkSplitRequested` (`Link`,
`Location` — ближайшая точка кривой, мировые координаты), и хост ставит туда свой узел с `Reroute` в
шаблоне и вместо одной связи заводит две; `Location` — где быть центру перевалки, и хост вычитает
половину её размера (`NodeEditor.Reroute.Size`). Второе нажатие двойного щелчка выбирает связь, как
щелчок, но отцепления не начинает; с модификатором добавления двойной щелчок — жест выбора и ничего
не просит. В безголовых тестах время стоит, и два нажатия в одной точке — всегда двойной щелчок:
тесты, щёлкающие одну связь дважды подряд, получают запрос излома.

`Reroute` — вход и выход в одной точке в центре кольца; ключи портов — `Input` и `Output`, задавать
оба. Попав в `Node`, он ставит узлу `:reroute`, и тема снимает карточку — стиль стоит после
`:selected`, иначе у выбранной перевалки вернулась бы рамка карточки. Выбор узла перевалка повторяет
своим `:selected`. У её портов нет фона: прозрачный фон делает нажимаемой всю рамку порта, и две рамки
18 × 14 закрыли бы почти всё кольцо — нажимать по центру значит тянуть связь из выхода (его штырёк
сверху), по кольцу — тянуть узел.

**Порты в одной точке разрешаются направлением**: протягиваемый конец берёт ближайший порт, а из
стоящих с ним в одной точке (в пределах полуединицы мира) — тот, что может его принять. Шире правило
делать нельзя: первая версия предпочитала принимающий порт во всём радиусе захвата, и конец,
брошенный на выход узла, уходил во вход строкой выше, в 17 px, — поймали это прежние тесты отказа.

**Разрез** — Alt + протяжка левой по пустому холсту или по связи (`LinkCutModifiers`; `None`
выключает): отрезок от нажатия до указателя, перечёркнутые подсвечиваются `:cutting`, на отпускании —
один `LinkDeleteRequested` в порядке коллекции хоста. Правая кнопка занята контекстным меню на
нажатии, средняя — панорамой, Ctrl — режимом контейнеров ядра. Начало отрезка хранится в мировых
координатах, поэтому автопрокрутка у края не сдвигает его. Пересечение — отсев по `WorldBounds`, затем
отрезок против той же ломаной из 24 отрезков; **точка на прямой считается лежащей по одну сторону**:
середина симметричной связи — вершина ломаной, и при строгом сравнении разрез ровно через неё не
пересекал ни одного из соседних отрезков. Нажатие по узлу разрезом не становится: узел берёт его
обработанным, и до редактора оно не доходит.

**Связи на миникарте** рисует слой `LinkMinimapLayer`, служба редактора: той же кубической кривой,
только разрешённые, кистью связей (`NodeEditor.Link.Stroke`).

### Стенд стоимости

`NodeGraphCostProbeTests` — графы на 200 и 2000 узлов рядами, цепочкой внутри ряда. Утверждает то,
что не зависит от машины и JIT: пересчёт связей за кадр перетаскивания — ровно степень узла при любом
размере графа; точное расстояние меряется только у связей, чья рамка накрыла точку. Время
утверждается только у кадра перетаскивания — он в миллисекундах — и только ростом. Поиски стоят
микросекунды, и их отношение здесь не держится: первый замер в процессе идёт по неоптимизированному
коду даже после прогрева. Их время печатается.

Числа для решений — из прогона с `-c Release`: тесты идут в отладочной сборке, где код библиотеки не
оптимизирован вовсе и стоит в разы дороже. На машине разработки: проход мимо 1950 связей — около
8 мкс, поиск порта под свободным концом среди 4000 портов — около 8 мкс, наведение на 2000 узлах —
0,03 мс; кадр перетаскивания на 2000 узлах — около 2,5 мс и в 18 раз дороже, чем на 200. Поэтому
следующий этап — о раскладке и виртуализации, а не об индексе.

Две ловушки стенда, обе стоили замера. Узел, который тянут у края окна, тянут в полосе
автопрокрутки: на большом графе кадр идёт миллисекунды, таймер успевает тикнуть по настоящим часам,
и счётчик показывает не степень узла. А связь из конца ряда в начало следующего — обратная, её плечо
— половина пролёта, и рамка накрывает граф на всю ширину: отсев по рамке таких связей не отсеивает,
и индекс по рамкам не отсеял бы — ему понадобились бы отрезки кривой.

Второй этап добавил два вопроса. Ход разреза сверяет с кривой только связи, чью рамку задел отрезок —
короткий отрезок поперёк одной связи даёт ровно одну сверку при любом размере графа (`LinkCutChecks`);
ход через всё окно стоит около 1 мкс на 195 связях и 9 мкс на 1950. Перерисовка миникарты стоила
0,33 мс на 200 узлах и 1,36 мс на 2000 и случалась на каждом кадре; третий этап закешировал её
содержимое и проредил пересборку («Миникарта» выше), и перерисовка стоит микросекунды.

Третий этап добавил стенд с виртуализацией — `VirtualGraphCostProbeTests`: графы на 2000 и 10 000
узлов на моделях (`GraphModels.cs` — общая оснастка с тестами концов связей), с `ItemLocationBinding`,
`PortNodeBinding` и предполагаемым размером. Утверждает, что от размера графа не зависит: сколько
развёрнуто узлов и связей и сколько контролов связей создано при загрузке, что переставляет кадр
перетаскивания (узел и две его связи) и что перемеряет кадр панорамы (только развёрнутое). Замер —
общий, `CostProbe`. Числа `Release` на машине разработки: загрузка 125 мс и 408 мс, кадр перетаскивания
0,5 и 0,3–0,4 мс (без виртуализации на 2000 — 1,65), кадр панорамы 0,2–0,5 и 0,8–1,1 мс — он растёт
линейно: панели проходят все прямоугольники и записи, — перерисовка миникарты — микросекунды.

Четвёртый этап добавил в него малый масштаб: на 50 % — пороге — развёрнуто 140 узлов и 140 связей
на обоих графах, на 30 % и 10 % — ничего, и кадр панорамы ниже порога не меряет ничего. Цену слоёв
упрощённого вида стенд не даёт — это растеризация, а заглушка платформы квадратична по фигурам; её
мерила консольная проба на Skia (ADR 0008): весь граф на 10 000 узлов — 17–24 мс на кадр процессором.

Стенд нашёл две цены, обе исправлены. Жест пишет положение в модель, модель сообщает об этом, и
слежение панели просило меру на каждом кадре — перемерялись все развёрнутые; теперь изменение модели
развёрнутого элемента меры не просит. И панель связей, стоящая в шаблоне раньше панели узлов, мерялась
первой и, не видя ещё виртуализирующей панели, разворачивала все связи графа — загрузка 10 000 узлов
стоила 2,9 с; теперь о виртуализации связей решает привязка положения.

## Публичная поверхность закреплена

`PublicSurfaceTests` сверяет слепок публичной поверхности каждой сборки со своим baseline — `PublicSurface.<сборка>.baseline.txt` — **до отдельного члена**, а не до типа. Четыре файла, а не один, чтобы диff в ревью сразу называл пакет, которому меняют обещание. Новый публичный член роняет тест: его нужно либо внести в baseline осознанно, либо сделать `internal`. Отдельные тесты запрещают утечку машин состояний, стратегий размещения, направляющих и деталей overlay.

Слепок включает значения по умолчанию у `AvaloniaProperty` и режим привязки по умолчанию, если он не односторонний (`[TwoWay]`): смена умолчания ломает потребителя и при этом не видна ни в одной сигнатуре. `{Binding Location}` без режима у двустороннего свойства пишет в модель, у одностороннего — нет.

Обновление baseline: `UPDATE_PUBLIC_SURFACE=1 dotnet test --filter Public_Surface`. Диff baseline в ревью и есть тот артефакт, ради которого тест существует.

До этого закреплялся только список из 40 типов, и этого не хватило: `SelectTarget` — первый публичный член, добавленный после появления замка, — приехал с девятью дефектами, не уронив ни одного теста, потому что список типов не изменился.

Машины состояний (`*.States.*`), стратегии размещения (`ArxisStudio.Surface.UiDesigner.Placement.*`), резолверы направляющих (`ArxisStudio.Surface.Editing.*Resolver`), швы ядра и службы инструментов, `SelectionAdornerLayer`, `SelectionAdornerInfo`, `UiDesignerPanel` и свойства `SecondarySelectionAdorners` — **internal**. Вместе с ними internal стали `CurrentState`, `PushState`, `PopState` на обоих контролах.

Это работает потому, что AXAML компилируется в сборку, а компилятор XAML уважает `InternalsVisibleTo`: internal-типы в шаблонах и `TemplateBinding` к internal-свойствам разрешаются и в своей сборке, и в дружественной. Прецедент был давно — `UiDesignerPanel` в `ItemsPanelTemplate`.

Компилятор Avalonia добавляет публичные `CompiledAvaloniaXaml.*`; тест их отфильтровывает — они не наши.

## Инструменты разработки

`AvaDevTools` подключён **только к демо** — к обоим — и только под `#if DEBUG` — `this.AttachAvaDevTools()` в `App.Initialize`. На приложении, а не на окне: тогда дерево инструментов укоренено в `Application`, каждое окно — его узел, и F12 из любого открывает один и тот же DevTools. Вызов у окна инспектировал бы только его, и разница проявилась бы в тот день, когда у демо появится второе окно. Библиотека от него не зависит, в её `.nupkg` он не попадает: демо непакуемо (`IsPackable` выключен в `Directory.Build.props`).

Зачем он здесь: Avalonia 12 не поставляет `Avalonia.Diagnostics`, и без него живое дерево, значения свойств, разбор раскладки и источник стилей смотреть нечем. `F12` открывает окно инструментов, `Shift + F12` замораживает popup'ы и hover-состояния (иначе контекстное меню и подсказки пропадают ровно в момент, когда их надо рассмотреть), `Ctrl + K` — поиск по элементам, ресурсам и свойствам.

Лицензия — **freeware, не open source**: бесплатно для любого использования, включая коммерческое, но с запретом изменять, декомпилировать и продавать отдельно, и распространять можно только неизменённым в составе приложения. Для зависимости времени разработки, которая никуда не поставляется, это ограничение ни на что не влияет; знать о нём стоит, если демо когда-нибудь начнут выпускать бинарно.

### Четвёртый способ проверки — MCP

Главное для работы над этим репозиторием: DevTools умеет поднимать **MCP-эндпоинт на loopback**, и тогда агент читает то же, что видно в окне, — без скриншотов.

Сервер уже настроен: адрес записан в `.mcp.json` в корне репозитория, а поднимается он ключом у скилла `run-demo`.

```bash
powershell -ExecutionPolicy Bypass -File .claude/skills/run-demo/scripts/demo.ps1 -Action start -Mcp
```

Ключ выставляет `AVA_DEVTOOLS_MCP=1` дочернему процессу — то же самое, что запустить exe с этой переменной вручную. **Без ключа порт не открывается**, и это осознанно: обычный запуск демо не должен слушать сеть. Из кода то же включается через `this.AttachAvaDevTools(new DevToolsOptions { McpServer = true })`, порт меняется `McpPort` или `AVA_DEVTOOLS_MCP_PORT`; в репозитории этот путь не используется как раз потому, что он включал бы сервер всегда.

Чем это дополняет три уже описанных способа: headless-тест закрепляет поведение, скриншот проверяет рендер, канал автоматизации отвечает про публичный API редактора, а MCP отвечает про **живое дерево и оформление** — чего в этом репозитории как раз не хватало. `get_element` показывает применённые значения и приоритет каждого, `get_styles` — какой сеттер выиграл и в какой строке XAML объявлен, `explain_layout` — почему элемент такого размера, `get_problems` — сломанные привязки и дублирующиеся ключи ресурсов. Дефект с рамкой группы, которая рисовалась как заблокированная, читался бы отсюда сразу: политики видно значениями, а не по цвету на картинке.

Разрешения раздельные и по умолчанию закрыты. Сервер слушает только `127.0.0.1`; ввод (`click`, `type_text`, `press_key`, …) включается отдельно через `McpAllowInput` / `AVA_DEVTOOLS_MCP_INPUT=1`, заморозка popup'ов — через `McpAllowHold`. Проверено: вызов `click` при выключенном вводе отвечает отказом и объясняет, чем он включается. Мышь и клавиатуру поэтому по-прежнему ведёт `run-demo`, а MCP отвечает на вопросы о состоянии — эти два способа дополняют друг друга, а не заменяют.

Проверено на живом дереве: `get_element` у `PART_GroupSelectionAdorner` отдаёт `ResizePolicy = All`, `MovePolicy = Both`, `IsInteractive = True`. Ровно эти числа и были `None`/`None`, когда рамка группы рисовалась как заблокированная, — то есть дефект читался бы отсюда сразу, без скриншотов и без догадок про оттенок серого.

Первый же `get_problems` со сканированием прошёл 808 элементов и 1506 привязок: сломанных привязок нет, но есть **17 ошибок доступности** — кнопки шапки объявляются классом своего содержимого (`Avalonia.Controls.PathIcon`, `Avalonia.Controls.StackPanel`), потому что имени у них нет. Это оформление демо, а не библиотеки.

## Хрупкие места

Не ломает компиляцию — падает молча, в рантайме.

**Обратный масштаб оверлеев привязан к `ViewportZoom`, а не к `ViewportTransform`.** Это выглядит мелочью, но держит две вещи сразу. Прежний конвертер брал матрицу из `TransformGroup.Children[0]`, то есть зависел от порядка элементов в группе. И перевычислялся он только при смене **идентичности** привязанного значения, а трансформации редактор мутирует на месте — поэтому `UpdateTransforms` был вынужден пересобирать обе группы заново на каждом кадре панорамирования, инвалидируя все привязки шаблона. Замер это подтвердил: снимаешь пересборку — и оверлеи перестают следовать за зумом. Число меняется само, и оба костыля отпали.

**Свойство зависимостей, к которому привязан шаблон, не может быть `private`.** `TemplateBinding` в скомпилированном AXAML обращается к статическому полю `AvaloniaProperty`, а генерируемый для словаря класс лежит рядом с `UiDesignerView`, а не внутри него. Компилятор при этом молчит: сборка проходит с 0 предупреждений, и ломается только загрузка темы — в тестах это выглядит как 225 падений разом, ни одно из которых не про видимость. Поэтому `SecondarySelectionAdornersProperty` остаётся `internal`, хотя вызывающих у него в коде нет.

**Адорнеры позиционируются двумя независимыми механизмами.** Primary/group — через `Canvas.Left/Top` + `MultiBinding` со `ScaleDoubleConverter` + обратный `RenderTransform` в шаблоне. Secondary — через `SelectionAdornerLayer` с собственными `MeasureOverride`/`ArrangeOverride` и своим inverse-`ScaleTransform` на каждого ребёнка. Правку геометрии выделения нужно вносить в оба места.

## Выглядит ошибкой, но верно

Три места, которые уже были ошибочно опознаны как дефекты. Прежде чем «чинить» — прочитать здесь.

**`UiDesignerItem` ничего не закрашивает: его `Background` — `Transparent`, и это не «забыли задать».** `Transparent` и `null` для Avalonia не одно и то же: прозрачный фон участвует в hit-testing'е, отсутствующий — нет. Контейнер обязан отвечать на нажатие всей своей площадью, в том числе там, где содержимое ничего не рисует, — иначе клик по пустому месту формы не попадает никуда. Отсюда следствие, которое и принимают за дефект: **форма, не задавшая себе фон, показывает то, что за контейнером,** то есть холст. Карточку под форму рисует хост — это его оформление, а не наше. Поменять `Transparent` на цвет здесь значит навязать этот цвет каждому потребителю и заодно объяснить ему, почему форма не той расцветки, чем документ.

**`SelectionAdornerLayer.MeasureOverride` смешивает единицы**: позиции мировые, размеры умножены на зум. Это конвенция слоя. Каждому ребёнку `UpdateChildTransforms` вешает обратный масштаб `1/zoom`, чтобы ручки не росли при приближении, а родительский Canvas масштабирует слой целиком: один зум гасится обратным трансформом, второй даёт итоговый размер. Уберёшь умножение — ручки поедут. Сам экстент ни на что не влияет: слой не обрезает содержимое.

**`Layout.UpdateSurfacePosition` пересчитывает `SurfaceX`/`SurfaceY` из фактического положения и «затирает» заданное.** Так и должно быть: где позицией распоряжается панель, координата поверхности обязана показывать, где контрол на самом деле. Драки за координату нет — стратегия размещения отсекает запись на шве. Флаг `IsUpdatingPosition` при этом настоящий, но работает **ниже** dispatcher-поста: в отложенном замыкании он не может быть истинным никогда.

## Известные дефекты

**Загруженная форма глуха к указателю, но не к клавиатуре.** В `ContentMode="Loaded"` ввод гасится одним свойством — `IsHitTestVisible="False"` на `PART_ContentPresenter` (`UiDesignerItem.axaml`). Указателя это лишает, клавиатуры — нет: содержимое остаётся в порядке обхода и остаётся интерактивным.

Замерено через MCP DevTools на демо:

- `get_tab_order` — **24 остановки из 32 лежат внутри редактируемых форм**: `ToggleSwitch`, `Slider`, `TextBox`, `ComboBox`, кнопки «Доброе утро», «Ушёл из дома». Tab из редактора уходит гулять по макету, а не по интерфейсу приложения.
- `type_text` в `TextBox` внутри формы **меняет содержимое макета**. Пользователь раскладывает форму, а печатает в неё.
- `Delete` при фокусе там удаляет символ, а не поднимает `DeleteRequested`; `Ctrl + A` выделяет текст, а не все элементы. Обе команды редактора теряются — это ровно то, ради чего `OnKeyDown` пропускает уже обработанные нажатия, и в этом случае правило работает против нас.
- Стрелки при этом **делают два дела разом**: выделение сдвинулось со 121 на 122, пока каретка стояла в том же `TextBox`. Нажатие неоднозначно.

Решение не однострочное, поэтому и не принято на ходу: убрать содержимое из обхода (`KeyboardNavigation.IsTabStop`/`TabNavigation` на презентере) — это правка темы, но она не закрывает программный перевод фокуса; отказывать в фокусе на уровне контейнера — надёжнее, но меняет поведение хоста, который мог на него рассчитывать. Выбор за владельцем библиотеки.

Здоровое, проверенное тем же прогоном: из 1454 привязок демо сломанных нет; дублей ресурсных ключей библиотеки нет (два предупреждения о затенении — осознанные переопределения демо); в логе Avalonia пусто. Все 17 ошибок доступности — на кнопках шапки демо, не в библиотеке.

## Состояние и что дальше

Сборка проходит с 0 предупреждений. Метод работы, который себя оправдал и которого стоит держаться: **сначала характеризующий тест или замер, потом реализация**, и обязательная проверка, что правка нагружена — временно откатить её и убедиться, что падают именно нужные тесты. Он несколько раз менял постановку задачи: вложенные контейнеры не давали выделения вовсе (а не «не тот scope»), проблема рамки была в латченном владельце (а не в обрезке), событий выделения было 22 за жест, а виртуализация оказалась не нужна вообще. (Цифра «1.28 мс на кадр при 500 элементах», стоявшая здесь, не воспроизводилась ничем: стенда в репозитории не было. Теперь он есть — `MarqueeCostProbeTests`, — но закрепляет он отношения, а не миллисекунды, и относится к разрешению владельца рамки, а не к кадру целиком. Числа про кадр целиком по-прежнему ничем не подкреплены, и в документе их нет.)

Сделано по дорожной карте: сетка, контракт изменений под undo/redo, клавиатура, события выделения, z-order, фиксация публичной поверхности, привязка к сетке, осведомлённость о раскладке (стратегии размещения, ограничение по контейнеру, перестановка среди соседей), snap lines и smart guides — на перетаскивании и на изменении размера.

Дорожная карта пройдена. Индикатор точки вставки настраивается ресурсом `UiDesigner.ReorderIndicatorBrush` — в шаблоне это обычный `Rectangle`.

Редактор узлов прошёл четыре этапа (ADR 0004, 0005, 0007 и 0008, «Редактор узлов» выше). Третий —
раскладка по изменениям, виртуализация узлов и связей и закешированная миникарта; четвёртый — малый
масштаб: ниже 50 % карточки без контейнеров. За ними — оформление узла (ADR 0009): заголовок, полоса
в обоих видах и цвет провода из модели, — и выбор без контейнеров (ADR 0010): «выбрать всё» на 10 000
узлах — десятки миллисекунд вместо 53 секунд. Числа — в «Стенде стоимости» и в ADR. Кандидаты на
следующий: кадр перетаскивания всего большого выбора — 99 мс на 10 000 узлах, почти всё — запись
привязкой и её перечитывание, отвергнутый путь «двигать видом, писать на отпускании» в ADR 0010; рамка
карточки ниже второго порога — 6 из 17–24 мс кадра; пространственный индекс — когда линейный проход
кадра панорамы (около 1 мс на 10 000) станет заметен; удаление всего графа в 2 с, по событию коллекции
на каждый узел и связь.

## Решения

`docs/adr/` — решения, которые ограничивают будущую работу, с причиной. Записывать туда стоит то,
у чего есть очевидная альтернатива, отвергнутая по причине, которую иначе переоткроют.

| --- | --- |

| [0002](docs/adr/0002-where-the-group-mark-lives-belongs-to-the-document-owner.md) | Смысл группы — за редактором, место её хранения — за владельцем документа |
| [0003](docs/adr/0003-the-library-is-three-layers-and-references-go-down.md) | Библиотека — три слоя (`Surface`, `Surface.Editing`, `Surface.UiDesigner`), ссылки идут только вниз |
| [0004](docs/adr/0004-the-node-editor-is-a-fourth-layer-beside-the-form-designer.md) | Редактор узлов — четвёртый слой рядом с дизайнером интерфейса; связь знает концы данными портов, структуру графа правит хост |
| [0005](docs/adr/0005-a-bend-is-a-reroute-node-and-the-minimap-is-a-surface-tool.md) | Излом связи — узел-перевалка хоста, разрез — удаление перечёркнутых, миникарта — инструмент любой поверхности |

| [0007](docs/adr/0007-containers-follow-the-viewport.md) | Контейнеры следуют видимой области: раскладка по изменениям, виртуализация узлов и связей по `ItemLocationBinding`, миникарта рисует закешированное |
| [0008](docs/adr/0008-the-small-zoom-is-drawn-not-realized.md) | Малый масштаб рисуется: ниже `SimplifiedZoom` карточки без контейнеров с полосой из `ItemAccentBinding`, связи — слоем, нажатие разворачивает |
| [0009](docs/adr/0009-the-node-card-has-a-header-and-the-host-designs-it.md) | У карточки узла есть заголовок, а дизайн задаёт хост: полоса у контейнера ядра в обоих видах, `Node.Header` и `ItemHeaderBinding`, цвет провода из модели, базовый вид — темами |
| [0010](docs/adr/0010-selection-is-data.md) | Выбор — данные, контейнер — вид: `SelectedItems` — полный выбор, `SelectedTargets` — развёрнутое; событие — о выборе; свёрнутое двигается записью в модель, сдвиги — в `ItemChanges` |

`SelectTarget(control, additive)` — единственный публичный способ задать выделение, который меняет **оба** слоя. Внутри него порядок существенный и в обратном тихо не работает: очистка индексного выбора приходит в обработчик, а тот на пустом выборе вычищает и слой target'ов. Оба слоя обязаны меняться вместе — см. «Двухуровневое выделение».

Унаследованные от `SelectingItemsControl` `SelectedIndex`, `SelectedItem`, `SelectedItems` и `Selection` тоже публичны и тоже пишут выделение — но **только индексный слой**. Контейнер, попавший туда без записи в слое target'ов, читается как «выбран его вложенный контрол по умолчанию», а не как «выбрана форма целиком». Закрывать эти двери не нужно, они часть контракта `SelectingItemsControl`; знать про них нужно.

## Заметки по Avalonia 12

Проект недавно мигрировал с 11.3.9 (коммит c1823d5). При переносе кода из 11.x-примеров учитывать:

- `GetVisualRoot()` удалён вместе с публичным `IRenderRoot`; `RenderScaling` берётся с `TopLevel.GetTopLevel(this)`
- `Visual.VisualRoot` — `protected`, снаружи использовать `IsAttachedToVisualTree()`
- `VisualTreeAttachmentEventArgs.Root` устарел → `RootVisual`
- `TextBox.Watermark` → `PlaceholderText`
- `BindingPlugins` стал internal; валидация DataAnnotations теперь opt-in через `AppBuilder.WithDataAnnotationsValidation()`
- `Avalonia.Diagnostics` (DevTools) для 12.x не выпущен: встроенного F12 в Avalonia 12 больше нет. В **демо** его заменяет `AvaDevTools` — сторонний пакет (Pavel Zheltiakov), подключённый осознанно; см. «Инструменты разработки». В библиотеке зависимости на него нет и быть не должно.
