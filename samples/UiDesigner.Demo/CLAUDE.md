# CLAUDE.md

Демо-приложение `UiDesigner.Demo`. Файл грузится, когда работают под этим каталогом; про саму
библиотеку сказано в `CLAUDE.md` в корне репозитория.

Демо — конструктор форм на трёх семействах разом: холст и жесты даёт `ArxisStudio.Surface`, документ
и каждую его правку — `ArxisStudio.Markup`, проект, сборку и запуск —
`ArxisStudio.ProjectSystem`. До 2026-09-30 он был образцом `samples/FormsDesigner` в ProjectSystem и
переехал сюда целиком, заменив прежнее демо с экранами умного дома (ADR 0021). Что он умеет и почему
устроен так, рассказывает его [README.md](README.md) — по-английски, как и код.

## Что отличает его от остального репозитория

**Комментарии и README — английские.** Код написан под правило ProjectSystem и приехал как был;
переводить шестнадцать тысяч строк при переносе не стали (ADR 0021). Новый комментарий в этом
каталоге пишут по-английски, чтобы файл не читался на двух языках. Исключение — `Automation/`: канал
пришёл из прежнего демо, и он русский.

**Ему нужны соседние репозитории.** `ArxisStudio.ProjectSystem` и `ArxisStudio.Markup` должны лежать
рядом с этим. Без первого проект падает с `SURFDEMO01`, без второго — адаптер ProjectSystem со своей
фразой. У головной студии они лежат рядом всегда: все три — подмодули `external/`.

**Две настройки сборки у него свои**, и обе названы в проектном файле с причиной. Глобализация
инвариантная: под ней демо написано, и даты списка недавних на неё опираются; `--verify` проходит и
без неё, но дробные числа в инспекторе этим не проверены, поэтому она оставлена. Конфигурация
передаётся проектам соседних репозиториев: без этого сборка Release связалась бы с их Debug.

**Пересборка идёт через три репозитория.** `dotnet build samples/UiDesigner.Demo` собирает и
ProjectSystem, и Markup. Живое демо держит их сборки так же, как сборки Surface: перед пересборкой
его закрывают.

## Ключи запуска

Без аргументов открывается экран приветствия. Путь к проекту его пропускает, имя формы открывает её
сразу.

| Ключ | Что делает |
| --- | --- |
| `<проект> [форма…]` | открыть проект и формы, минуя приветствие |
| `--active <форма>` | какая из открытых форм показана |
| `--view design\|xaml\|split` | что показывает середина окна |
| `--theme light\|dark` | в какой вариации открыться; без ключа — тёмная |
| `--shot <файл.png>` | дождаться, пока окно успокоится, записать снимок и выйти |
| `--verify <пустая папка>` | сквозная самопроверка: написать в папку проект, открыть его, разложить, собрать, запустить; последняя строка — `CHECK VERDICT ok …` |
| `--stress <папка>` | цикл выносливости вместо прямой проверки |
| `--reclaim <папка>` | замер возврата поколения типов (адаптер ProjectSystem, его ADR 0023) |
| `--live <папка>` | дизайнер рядом с IDE: написать проект, открыть его, сохранять форму и код так, как сохраняет Rider, собирать проект рядом с IDE, менять типы и перезапускаться; последняя строка — `CHECK VERDICT ok …` |
| `--resume <файл>` | принять сессию, переданную прежней копией при перезапуске: проект, формы с текстом, вкладку впереди, масштаб; принятие — стёртый файл |
| `--probe` | не перезапускаться на неудачном возврате, а назвать, кто держит поколение |
| `--automation <каталог>` | канал управления редактором, см. ниже |

Все ключи, кроме `--probe`, берут значение. `--verify`, `--stress` и `--reclaim` собирают и запускают
настоящий проект, `--live` — собирает; идут они десятки секунд, на холодном MSBuild — минуту и дольше,
и пишут шаги в стандартный вывод строками `CHECK …`.

Запускать для проверки нужно **собранный exe**, а не `dotnet run` из шелла: процесс, породивший его,
умирает вместе с командой и уносит демо.

`--shot` рисует окно само в картинку (`RenderTargetBitmap`), мимо композитора. Этого хватает для
цветов и раскладки; то, что рисует композитор, — всплывающие окна, кеш миникарты — видно только
снимком самого окна, и его делает скилл `run-demo` (`PrintWindow`).

Тему снимка задаёт `--theme`: переключатель в шапке меняет её у живого окна, а скрипту его не нажать.

`--verify` дописывает созданный проект в список недавних —
`%AppData%/ArxisStudio/UiDesigner.Demo/recent.json`. Список сам выбрасывает то, чего на диске уже
нет, когда его читают.

`--live` играет вторую сторону — IDE, которая пишет те же файлы. Файл формы он сохраняет так, как
Rider: текст во временный файл, исходный переименован в сторону, временный — на его место, исходный
удалён. Проверяет, что форма идёт следом, что история и «изменено» говорят правду, а запись поверх
несохранённого — вопрос, а не потеря. Часть 1 плана: L1, L2, привязка из инспектора по
дизайн-данным, отмена и повтор поперёк внешней правки. Часть 2 (`StudioCheck.Live.Builds.cs`) — проект:
сохранение формы в IDE не перечитывает проект (версия снимка та же), новый файл перечитывает его один
раз, а после обычного `dotnet build`, наполнившего `obj/Debug`, своя сборка дизайнера по сохранению
кода проходит — и проходит снова, пока собранное IDE приложение держит `bin/Debug`. Части 1 и 2
держат замену типов (`SwapsHeldFor`), а часть 3 начинается, только когда они вернулись: формы,
которые они держали, построены под типами, которые она заменит.

Часть 3 (`StudioCheck.Live.Swaps.cs`, `.Library.cs`, `.Restart.cs`) — код. L3: модель
представления, сохранённая в IDE, собрана и заменена сама, без активации окна между сборкой и
заменой; вкладки, несохранённый текст с историей, выбор и масштаб на месте, стоп-кадр — только на
время замены. L4: жест на холсте — нажатие средней кнопки, поднятое на самом холсте, — держит
замену, отпускание её запускает. L5: приложение, запущенное из дизайнера, живёт через сборку и
замену. L7: решение из приложения и библиотеки — одно поколение, библиотека загружена один раз,
сохранённый класс библиотеки собран через приложение и заменён. L9: контрол, подписанный на процесс,
держит типы; позади другого окна дизайнер ждёт, впереди перезапускается сам, и новая копия по
каналу автоматизации отвечает теми же вкладками, несохранённым текстом, выбором и масштабом — потом
стенд останавливает её по номеру процесса. «Впереди» стенд отвечает за вид через `IsStudioActive`:
вывести окно вперёд скрипт на Windows не может. Каждая замена говорит фазы строкой
`CHECK timing`. Проекты он открывает мимо приветствия, и в список недавних они не попадают.

Часть 4 (`StudioCheck.Live.Controls.cs`) — контролы и данные проекта, в том же решении между L7 и L9.
L6: `UserControl`, который пишет IDE, палитра предлагает несобранным; брошенный на окно, он ждёт сборки
и замены — пока замена придержана, в документе его нет, — и встаёт после неё; правка его разметки в
IDE видна на окне при той же сессии окна; удаление — на месте. L8: модель представления выбрана типом
данных вида и дизайн-данными, `Text`, привязанный к ней, показывает дизайн-экземпляр, а член,
переименованный в IDE, делает привязку «broken». L10: окно с классом, обработчиком и `x:DataType`
меняется снаружи структурно — в панели рядом с кнопкой, потом ресурсами у корня; сессия та же,
обработчик бежит на окне, лишнего окна у платформы нет (окна процесса через `EnumWindows`). Шаг, после
которого типы требуют перезапуска, останавливает часть и называет держателя, а L9 тогда не идёт:
дальше шли бы шаги на поколении, от которого хост уже отказался.

## Чего в демо нет, и нарочно

Демо показывает дизайнер, и то, что им не было, снято по слову владельца (2026-09-30). Возвращать
это незачем, а новое того же рода — не добавлять.

- **Проекты демо не создаёт и не клонирует.** Экран приветствия — список недавних и «Open»; проект
  для ручной проверки пишет `--verify` в свою папку. Шаблонов,
  «New Project», «Clone from Git», разделов «Templates» и «Learn» нет; с одним разделом полоса слева
  стала меню из одного пункта и ушла вместе с ними.
- **`ProjectScaffold` — оснастка проверок, а не возможность.** Его зовёт только `StudioCheck`:
  `--verify`, `--stress`, `--reclaim` и `--live` нужен проект, который можно собирать и переписывать,
  и чужим он быть не может. Из интерфейса до него не дойти.
- **Вкладок «Problems» и «Packages» нет.** На что пожаловалась сборка или загрузка, пишется в консоль
  строками под счётом (`ShowDiagnostics`); коллекция `Diagnostics` осталась — её читают проверки.
  Что нашла загрузка формы, пишется туда же — всё, с файлом и строкой, при каждой смене её состояния
  (`ShowMarkupDiagnostics`). Строка ошибки начинается с «!», и по этому знаку консоль читают
  проверки; вопрос к человеку — файл изменён поверх несохранённого — этого знака не носит.
  Пакетов демо не ставит, и ссылки на `ArxisStudio.ProjectSystem.NuGet` у него больше нет. Контрол
  из тулбокса, которому нужен пакет, по-прежнему отклоняется с названием пакета.
- **Нарисованного, но не работающего, нет.** Сняты строка «Settings» и учётная запись на
  приветствии, чип размера с шевроном, который ничего не открывал, галочка рядом с именем выбранного
  и три слова строки состояния — «Avalonia 12.1.1 · net10.0 · UTF-8», — сказанные про любой проект,
  не спросив проекта. Правило на будущее: что выглядит нажимаемым — нажимается, что сказано про
  проект — у проекта и спрошено.

## Размер и растяжение в инспекторе

Контрол с собственной шириной не растягивается: ширина сильнее выравнивания. Дорог назад к размеру,
который решает раскладка, три, и каждую держит шаг `--verify` («a width comes out…»):

- **Кнопка `NaN` рядом с `Width` и `Height`** убирает атрибут из документа (`PropertyRow.ResetCommand`).
  Не пишет `Width="NaN"`: отсутствие атрибута и есть `NaN`, а документ остаётся таким, каким его
  написал бы человек. Пустое поле такого размера показывает `NaN` подсказкой — и только когда живой
  контрол подтверждает, что ширина у него `NaN`.
- **Пустое поле — «не задано», а не ошибка.** Прежде пустой текст шёл в `ConvertFromText`, тот
  отвечал «not a Double», и строка отказывалась писать: числовое поле нельзя было очистить вовсе.
  Проверка с выключенной правкой падает именно на этом.
- **`Stretch` отпускает размер своей стороны**: `HorizontalAlignment` — `Width`, `VerticalAlignment` —
  `Height` (`SizeReleasedBy`). Одной правкой документа, поэтому отмена возвращает и выравнивание, и
  число разом. Другую сторону не трогает.

У корня формы ни кнопки, ни отпускания нет: ширина окна — размер формы, и без неё карточка берёт
умолчание хоста, а не раскладку.

## Вид

Расстановка окна — мокапа ArxisStudio. Палитра, кегли и размеры — **не** мокапа, а дизайн-системы
студии (`docs/design-system.md` головного репозитория): мокап ей предшествовал и её порогов не
проходил. Правила ниже — её, и нарушаются они молча.

**Цвет — роль, число — темы студии.** `Views/Theme.axaml` называет, для чего цвет, и берёт значение у
той же роли в `ArxisStudio.Themes.Arxis` (`Palette.axaml`). Значения скопированы, а не подключены:
тема была бы третьим соседним репозиторием. Копию держит `--verify` — шаг «the palette holds its
contrast thresholds» меряет 62 пары в обеих вариациях и падает, называя пару и число. Новый токен
вносят в таблицу `PalettePairs` у `StudioCheck` вместе с поверхностями, на которых он рисуется; иначе
он не проверяется ничем.

**Акцент — три токена, состояние — два.** `Acc` — графика (значок, подчёркивание), `AccFill` —
заливка под белым текстом, `Lnk` — акцент словом. Один цвет всеми тремя быть не может: синий,
читаемый текстом на тёмной панели, слишком светел, чтобы нести белый текст. По той же причине у
ошибки и предупреждения есть `Red`/`Yel` для значка и `RedText`/`YelText` для слова, а у плиток с
белыми инициалами — свои `Mono*`. Поставить `Foreground` токеном графики — значит уронить порог, и
`--verify` этого не увидит: он меряет пары из таблицы, а не разметку.

**Текст по умолчанию наследуется от корня `.chrome`, а не ставится правилом на `TextBlock`.** Правило
`.chrome TextBlock` зависело от класса предка, а такой селектор применяется триггером — сильнее
значения, которое шаблон данных ставит ресурсом. `Foreground="{DynamicResource Fg3}"` в любом списке
было написано и не действовало: пути недавних проектов, типы в иерархии и подписи инспектора
рисовались основным цветом. Возвращать правило на `TextBlock` под `.chrome` нельзя.

**Класс основной кнопки — `primary`, не `accent`.** `accent` — класс самой темы Fluent, и кнопку с
ним она красит системным акцентом машины, что бы ни стояло в стиле демо.

**Кегли целые — 13, 12, 11; нажимаемое не ниже 24.** Дробный кегль кладёт глифы между пиксельными
сетками.

**Нажимаемое — кнопка или строка списка, а не рамка с обработчиком.** Недавние проекты приветствия,
вкладки форм и плитки файлов были рамками: `Tab` на них не вставал.
Состояния у кнопки четыре — под указателем, под нажатием, с клавиатурой на ней и выключенная, — и
ставятся они на `ContentPresenter` шаблона: там же красит свои тема, и правило на самом контроле до
них не доходит.

**Значок в кнопке рисуют цветом `Foreground` кнопки**, если он должен меняться под указателем:
`$parent[Button].Foreground`. Часть шаблона — `ContentPresenter` — среди логических предков пути не
числится, и привязка к ней молча даёт пустоту: крестик кнопки закрытия так и пропал на один прогон.

**Интерфейс — английский, весь.** Русские строки остались только во входных данных самопроверки
(`StudioCheck`) — значениях, которые она пишет в кнопку формы; заодно через документ и файл
проходит не-ASCII.

Окна вопросов собирает `Views/Dialogs.cs`: окно, сделанное кодом, начинает с вида темы, а не демо, и
класс `chrome` на корне с классом на каждой кнопке — то, что приносит в него правила инструмента.

Перетаскивание из тулбокса по-прежнему только мышью: клавиатурной замены у него нет.

## Канал автоматизации

`--automation <каталог>` поднимает канал из двух файлов — `command.json` и `response.json` — и
исполняет команды на потоке интерфейса. Команды и смысл ответа описаны в корневом `CLAUDE.md`; здесь
— что у этого демо иначе, чем у прежнего.

Канал привязан к редактору окна дизайнера, поэтому ему нужен открытый проект: с экрана приветствия
поднимать нечего. Контейнер у редактора один — `UiDesignerFormItem` активной вкладки: открытых
форм может быть несколько, а на холсте лежит одна.

`select` адресует контрол по `Name`, то есть по `x:Name` из документа. У формы без имён адресовать
нечего, кроме контейнера (`selectContainer`). `tree` перечисляет всё именованное в визуальном дереве
контейнера, включая части шаблонов (`PART_…`) — выбирать их незачем, авторская разметка в списке
ниже.

`state` отвечает и за дизайнер (`designer`): вкладки с текстом документа, «изменено» и выбором
каждой, вкладка впереди, выбор на холсте, масштаб, состояние типов и имя поколения. Этим отвечает
копия, поднятая перезапуском, — так `--live` спрашивает, что она приняла.

Команды дизайнера адресуют по именам, а не по точкам экрана, и идут дорогой человека
(`DesignerViewModel.Automation.cs`): форма — по имени файла, элемент — по `x:Name` (без имени — корень),
элемент палитры — по контролу, который он ставит. Каждая ждёт того, что начала, и отвечает
состоянием дизайнера после; не вышло — `ok: false` и причина в `error`. Следующая команда не читается,
пока не ответила предыдущая.

| Команда | Поля | Что делает |
| --- | --- | --- |
| `open` | `form` | открывает форму проекта и ждёт показа |
| `drop` | `entry`, `parent`, `index` | ставит элемент палитры в элемент с этим именем на этот индекс содержимого (без индекса — в конец); контрол проекта без сборки собирается и встаёт после замены |
| `edit` | `target`, `property`, `value` | пишет свойство, как строка инспектора; `x:Name` переименовывает |
| `bind` | `target`, `property`, `path` | пишет `{Binding path}` |
| `undo`, `redo`, `save` | — | команды формы впереди; `executed` — исполнилась ли |
| `reload` | — | перечитывает файл формы впереди, как хост на его перемену; `result` — чем кончилось |
| `build` | — | собирает набор дизайна, как хост; `result` — итог сборки |
| `swap` | — | меняет типы сейчас, что бы её ни держало; `result` — фазы или отказ |
| `handoff` | — | что перезапуск передал бы новой копии сейчас, не перезапускаясь |

Места точкой у `drop` нет: место — слово указателя, и `Canvas` получает ребёнка в начале координат.

`nudge` по контролу в `StackPanel` ничего не меняет, и событий правки не будет: положением
распоряжается раскладка, и редактор отсекает такую запись на шве. Это ответ, а не поломка канала.

Правка, которую канал провёл через редактор, доходит до документа той же дорогой, что жест: редактор
поднимает `EditCompleted`, и окно записывает её в разметку (`MainWindow.OnEditCompleted`).

## DevTools

`AvaDevTools` подключён под `#if DEBUG`, на приложении: окон у демо два — приветствие и дизайнер, — и
вызов у окна инспектировал бы одно. `F12` открывает инструменты из любого. MCP-эндпоинт поднимает
ключ `-Mcp` у скилла `run-demo`, порт 5174.

Подключённые инструменты проверкам не мешают, и это замерено, а не предположено: в отладочной сборке
`--verify` заканчивается `VERDICT ok`, а `--reclaim` отвечает «provably dead» на все три случая — так
же, как в Release. Возврат поколения известен тем, что отвечает по-разному от запуска к запуску
(`docs/limitations.md` в ProjectSystem), поэтому `--reclaim` гоняют трижды. Если «still held» начнёт
появляться только в Debug, первыми смотреть на инструменты: они держат дерево живого окна. Список
окон инструментов (`DevToolsExtensions.s_trackedWindows`) держит каждое открытое окно процесса —
и копию корня, которую никто не закрыл; закрытые он отпускает. Окно, найденное там, держится и без
инструментов: на Win32 незакрытое окно переживает любую сборку мусора.

## Базовые замеры

Сняты 2026-10-02, перед переносом инфраструктуры дизайнера в библиотеки: Debug, собранный exe,
пустые папки. С ними сравнивают, когда замена поколения переедет в хост дизайна.

| Режим | Вердикт | Время |
| --- | --- | --- |
| `--verify` | ok | 47 с |
| `--stress` | 1 шаг: цикл 3 — «changed on disk and has unsaved edits here» | 30–35 с |
| `--reclaim` ×3 | все три случая «provably dead» | 10–11 с на прогретом MSBuild, 95 с на холодном |

Возврат поколения (`CHECK timing`): случай 1 — 145–163 мс, случай 2 — 107–110 мс, случай 3 — разборка
90–113 мс и возврат 110–112 мс.

`--stress` падает на гонке, а не на правке: запись «другого редактора» приходит, пока у формы есть
несохранённые изменения, и демо оставляет свои, не сказав, что файл на диске теперь другой. Это
поведение и меняется планом — внешняя правка станет шагом истории, а расхождение — вопросом к
человеку.

Что нашлось, пока база снималась:

- **Пересборка формы не закрывала окно, которое заменяла.** `RebuildFromAsync` отставлял сессию, а
  корень-окно оставался открытым. На Win32 окно, ни разу не показанное и не закрытое, переживает любую
  сборку мусора, а закрытое уходит — это проба на голом Avalonia 12.1.1, без демо. Через такое окно
  держалось всё поколение: случай 3 `--reclaim` отвечал «still held» в восьми прогонах из одиннадцати —
  когда наблюдатель успевал пересобрать открытую форму. Отставленный корень теперь закрывает
  `CloseRetiredRoot`, и при замене, и при пересборке; держит это шаг 5b `--verify`.
- **Шаг 6 `--verify` не видел ошибок сборки.** Он сравнивал серьёзность со строкой `"ERROR"`, а
  `DiagnosticRow` нёс `"Error"`. Серьёзность теперь перечисление, все шаги спрашивают один предикат
  `Errors`, и подшаг со сломанной сборкой проверяет, что проверка видит.
- **Проба держателей отвечала «inconclusive».** Весь бюджет уходил на типы, ставившиеся в очередь при
  каждом упоминании, на упакованные числа и указатели и на графы MSBuild. Теперь объект попадает в
  обход один раз, массивы чисел и объекты MSBuild и NuGet не обходятся, слабые таблицы обходятся по
  живым ключам, засеваются статические поля всех сборок, кроме движков, а исчерпанный бюджет называет
  типы, на которые ушёл.
- **Перезапуск предлагался по подстрокам.** Класс, которого ещё нет в сборке (`AXM3020`), — повод
  собрать, а не перезапустить; слова Avalonia «Unable to substitute» и «Could not load type» читаются
  теперь только в диагностиках, которые несут её текст.

### После вехи 17 Markup (этап 1 плана)

Корень формы с окном демо больше не отдаёт руками: `FormRootAccess` отвечает на `IXamlRootAccess`
Markup, и сессия сама просит у карточки содержимое окна на время каждой своей записи. Структурного
сопоставления размещённых контролов (`DesignerViewModel.Foreign.cs`) и `TakeOffTheCanvas` больше нет —
карта Markup называет размещённый контрол сама, и удаление его проходит на месте. `--reclaim`
заканчивается шагом на окне, открытом под преемником, — чей класс разрешился: панель меняется
снаружи рядом с кнопкой, чей `Click` объявляет класс, и правка ложится на месте, сессия та же,
обработчик бежит на окне.

| Режим | Вердикт | Время |
| --- | --- | --- |
| `--verify` | ok | 51 с |
| `--stress` | тот же 1 шаг: цикл 3 (это этап 2 плана) | 29 с |
| `--reclaim` ×3 | все три случая «provably dead», и шаг с обработчиком | 11 с |

Возврат поколения: случай 1 — 208–222 мс, случай 2 — 172–180 мс, случай 3 — разборка 80–94 мс и
возврат 176–190 мс. Дольше базы на паузы между раундами (ниже).

Что нашёл стенд по дороге:

- **Форма с приватным обработчиком не загружалась вовсе.** Шаг с кнопкой первым делом упал на
  загрузке окна: динамическая сборка рантайм-загрузчика Avalonia не достаёт до `private`-метода
  класса, если загрузке не назван `LocalAssembly`, — а обработчик в code-behind приватный как
  правило. Сессия Markup теперь называет сборку класса сама (его ADR 0019).
- **«still held» без держателя.** К вечеру тот же код, что утром отвечал «provably dead», в случае 3
  отвечал «still held» девять раз из десяти — и базовый код тоже, это проверено рабочим деревом на
  `8a49411` с Markup на `df65cdf`. Проба, спрашивавшая дольше, находила поколение мёртвым через
  0,2–0,7 с, но только если интерфейсу давали ходы диспетчера, а не одно время; в очереди в этот
  момент стояло одно задание рендерера. Кадр, который рендерер не дорисовал — указатель над
  дизайнером, — держал свои контролы, а десять сборок подряд не давали ему закончить. Возврат в
  адаптере ProjectSystem теперь спрашивает не меньше двух секунд, с ходом диспетчера и паузой между
  раундами (его ADR 0023, дополнение), и случай 3 отвечает за 0,2 с.

### После вехи 18 Markup (этап 2 плана)

Форма открыта живым документом Markup (`XamlLiveDocument`, его ADR 0025), и своего у демо стало
меньше. История отмены — у формы, а не у демо (D2); «изменено» — разница текста с сохранённым, и
отмена до сохранённого возвращает форму в «сохранено». Внешняя правка чистой формы — шаг истории
«Changed outside the designer», а правка поверх несохранённого ничего не меняет до ответа: над
холстом плашка «Take the file» / «Keep mine» (D13). Выбор помнится путём элемента у каждой формы, и
сохранение фоновой вкладки его не трогает (D15). Копирование, вставка, дубликат, обёртка и
пространство имён дизайна — готовые правки Markup: `XamlFragment`, `InsertFragment`,
`DuplicateElement`, `WrapElement`/`UnwrapElement`, `QualifyAttribute` (D16). У инспектора раздел
«Data»: тип данных в области и дизайн-данные спрашиваются у сессии, члены и путь привязки — у
`XamlMemberResolver`, по именам (его ADR 0026); строка свойства предлагает члены и пишет
`{Binding …}`, путь, которого у данных нет, помечен «broken», а «Create» пишет `Design.DataContext`
(D17). Каркас проекта пишет `Design.DataContext` рядом с `x:DataType`, как шаблон Avalonia. Что нашла
загрузка формы, пишется в консоль целиком (D18).

| Режим | Вердикт | Время |
| --- | --- | --- |
| `--verify` | ok | 42–63 с |
| `--stress` | ok: цикл 3 проходит | 29–30 с |
| `--live` | ok | 16–17 с |
| `--reclaim` ×3 | все три случая «provably dead» | 12–14 с |

Возврат поколения: случай 1 — 204–218 мс, случай 2 — 172–183 мс, случай 3 — разборка 64–82 мс и
возврат 196–309 мс. Случай 3 дольше этапа 1 на дизайн-данные (ниже).

Что нашёл стенд по дороге:

- **Позднее эхо своего сохранения читалось конфликтом.** `--stress` сохранял форму и правил её
  снова, а наблюдатель приносил текст того сохранения, когда у формы уже были новые правки: демо
  спрашивало человека о файле, который само и записало. Живой документ отвечает на текст, равный
  сохранённому, `AlreadySaved` при политике `ApplyIfClean` (дополнение к ADR 0025 Markup), и цикл 3
  `--stress` проходит — тот, на котором падали база и этап 1.
- **Дизайн-данные держали поколение.** С `Design.DataContext` в каркасе случай 3 `--reclaim` отвечал
  «still held», и проба назвала держателя: плагин привязок Avalonia помнит, умеет ли он читать имя у
  типа, словарём по типу и имени на всё время процесса, и модель представления проекта становилась
  ключом с первой же привязки. Возврат в адаптере ProjectSystem вычищает и его (его ADR 0023, второе
  дополнение); отсюда лишняя десятая секунды случая 3.
- **`--verify` проверял обёртку написанием.** Markup ставит обёрнутую кнопку на свою строку со своим
  отступом, и проверка `<Border><Button` перестала её узнавать; теперь она спрашивает структуру
  документа.
- **Диагностики формы не доходили до человека.** Форма с типом, которого ничто не разрешает,
  говорила «did not load» без причины: причина лежала в коллекции, у которой нет панели.

### После этапа 3 плана (Surface)

Бросок из тулбокса решает редактор, а демо его только пишет (D7, D16; ADR 0024 Surface). `DragOver` окна
спрашивает `UiDesignerView.TryResolveDropPlacement` под указателем и рисует ответ `ShowDropIndicator`,
`Drop` спрашивает снова и отдаёт ответ `DesignerViewModel.Drop`. Место — по раскладке родителя:
между соседями `StackPanel` по правилу перестановки, ячейка `Grid`, точка `Canvas`, пустые рамка,
`ContentControl` и страница `TabControl`. Сниппет палитры становится фрагментом Markup в пространстве
записи (`ToolboxEntry.XmlNamespace`, по умолчанию Avalonia), место пишется на корень фрагмента правкой
(`Canvas.Left`/`Top`, `Grid.Row`/`Column`), и фрагмент встаёт `InsertFragment` перед соседом, которого
назвал редактор. `WithPosition`, `ParentFor`, `FormUnder` и `DeepestAt` удалены; `ResolvesAsync`
спрашивает тип в пространстве записи, а не в пространстве документа по умолчанию. Страницы `TabControl`
и содержимое `Expander` в палитре — `StackPanel`: странице только с текстом бросать было бы некуда.

`FormRootAccess` отдаёт корень сессии через `UiDesignerFormItem.SuspendRoot()` (ADR 0025 Surface), а не
`Root = null` и обратно: форма больше не гаснет на каждую запись.

`--verify` получил шаг 3a — `StudioCheck.Drops.cs`: бросок между двумя соседями панели формы, на
страницу `TabControl`, в ячейку `Grid` и в точку `Canvas`. Каждый спрашивается у документа (где элемент,
что на нём написано) и у холста (где стоит контрол против показанного индикатора) и откатывается
отменой. Бросают стенды так же, как окно: размещение редактора в точке, показ, запись
(`DropIntoAsync`, `PlaceAtAsync`).

| Режим | Вердикт | Время |
| --- | --- | --- |
| `--verify` | ok, с шагом 3a | 45–52 с |
| `--stress` | ok | 30–31 с |
| `--live` | ok | 16–17 с |
| `--reclaim` ×3 | все три случая «provably dead» | 12 с |

Возврат поколения: случай 1 — 218–220 мс, случай 2 — 172–182 мс, случай 3 — разборка 66–80 мс и
возврат 302–312 мс, на уровне этапа 2: отдача корня через `SuspendRoot` возврат не замедлила.

Что нашёл стенд по дороге:

- **Стенд бросал быстрее, чем холст догоняет документ.** Документ принимает бросок сразу, а живое
  дерево — мигом позже, и место, посчитанное по панели, до которой правка ещё не дошла, вставало перед
  только что брошенным контролом. Человеку так не успеть. Место теперь считается, когда сессия показывает
  текст формы и дети панели разложены (`CaughtUp`, `LaidOut`).
- **«В конец панели» — точка внутри её последнего ребёнка, а не угол панели.** `TextBox` с шириной стоит в
  панели по центру, и левый нижний угол панели ближе к широкому тексту над ним: правило перестановки
  честно ставило контрол перед `TextBox`. Ровно это и увидел бы человек по линии; стенд целится в того, кого
  имеет в виду (`AtEnd`). Порядок «TextBlock, TextBox, Button» шага 3 и щелчок шага групп держатся на этом.
- **«После последнего» — после последнего видимого.** К шагу 12 `--stress` форма переполнена: панель
  растянута на всё окно, а её последние дети ушли за нижний край формы, где бросок не принимается, — и
  человек туда не бросит. Прежний бросок дописывал в конец вслепую; стенд целится после последнего
  ребёнка, которого форма показывает.
- **«Встал на месте линии» — между теми же соседями, а не на той же высоте.** Панель формы центрирована, и
  вставка поднимает её на половину прибавленной высоты: разделитель вставал на 10 пикселей выше линии,
  стоя ровно между нужными соседями. У рамки отступа своя поправка: тема даёт `Separator` поле, и
  сравнивается начало ячейки, а не контрола (`SlotOf`).
- **Ячейки `Grid` Avalonia 12 считают промежуток в дорожку.** `ActualWidth` столбца включает
  `ColumnSpacing` после него; расчёт ячейки в Surface на это опирается и закреплён тестом.

### После этапа 4 плана (ProjectSystem)

Слежения своего у демо больше нет: каталоги проектов слушает `ProjectSourceWatcher` ProjectSystem,
пачку собирает `FileChangeCoalescer.ForChanges` — сохранение Rider через временный файл и два
переименования приходит одной правкой файла, перенос между папками — переименованием, — а что пачка
значит, говорит снимок (`SolutionSnapshot.Classify`, ADR 0025 ProjectSystem). Отбора шума по именам
(`bin`, `obj`, точки, `___jb_`, `~`, `.tmp`) нет: снимок сам знает, куда пишут его сборки
(`BuildDirectories`) и что объявляют проекты. Сохранённая форма — правка документа без переоценки,
сохранённый класс — сборка, новый или ушедший файл — одна переоценка; форма, переименованная или
перенесённая в IDE, — с папкой вокруг неё тоже — идёт за файлом с историей (`FormViewModel.MoveToAsync`
поверх `XamlLiveDocument.RetargetAsync`), а удалённая — с файлом или папкой — закрывается. Пачки
разбираются по одной, следующая ждёт предыдущую (D14).

Выход своих сборок — `MSBuildDesignOutput` ProjectSystem (ADR 0026, D21): `OutputPath=bin/ArxisStudio/`
и `IntermediateOutputPath=obj/ArxisStudio/`, базы на месте. Прежний глобальный `BaseOutputPath` делал
весь `bin/Debug` IDE элементами проекта. Restore перед своей сборкой — только когда нужен: у проекта
нет ничего из `RestoreOutputs` на диске, или изменился вход оценки, который restore не пишет сам.

| Режим | Вердикт | Время |
| --- | --- | --- |
| `--verify` | ok | 45 с |
| `--stress` | ok | 31 с |
| `--live` | ok, части 1 и 2 | 23–26 с |
| `--reclaim` ×3 | все три случая «provably dead» | 12 с |

Возврат поколения: случай 1 — 214–218 мс, случай 2 — 170–177 мс, случай 3 — разборка 79–88 мс и
возврат 314–321 мс, на уровне этапа 3.

Что нашлось по дороге:

- **Перенос файла между папками Windows сообщает удалением и созданием** — даже внутри одного
  рекурсивного наблюдения, это замерено тестом ProjectSystem. Форма, перенесённая в IDE, закрывалась
  бы в дизайнере; коалесцер теперь соединяет одно исчезновение и одно появление имени в пачке.
- **Служебные элементы оценки выглядели правкой проекта.** MSBuild называет `IntermediateAssembly` и
  `_OutputPathItem` элементами, и собственная сборка дизайнера, переписав `obj/ArxisStudio/App.dll`,
  читалась бы правкой объявленного файла и переоценкой. Нашёл это тест выхода дизайнерских сборок;
  `Classify` теперь не считает файлами проекта то, что лежит под его каталогами сборки.
- **Часть 1 оставляла проект несобираемым.** Шаг «сломанная привязка» пишет `{Binding Titel}`, а
  проект компилирует привязки (AVLN2000) — обычная сборка части 2 падала законно. Сохранение IDE в
  части 2 возвращает имя члена.
- **Просьба «press Reload» писалась ошибкой.** Знак «!» стоял у вопроса к человеку; по соглашению
  консоли вопросы его не носят.

Нагрузку шагов части 2 проверили порчей: переоценка на каждую пачку роняет шаг «save» (v12 → v13),
прежний перенос баз — шаг «build» (сгенерированный IDE `AssemblyAttributes.cs` становится элементом).

### После этапа 5 плана (хост дизайна)

Типы проекта держит `ProjectDesignHost` адаптера ProjectSystem (его ADR 0028), и демо — тонкий хост
над ним (ADR 0026 Surface). Своего порядка замены, поколений на проект, решений по подстрокам и
`DesignerViewModel.Live.cs` больше нет. У демо осталось то, что знает только дизайнер: участник замены
(`FormsParticipant` — формы запоминаются, закрываются и строятся заново), отсрочки (жест, ввод в
инспекторе, диалог, тяга), стоп-кадр холста, перезапуск с передачей сессии
(`DesignerViewModel.Restart.cs`, `--resume`) и запуск приложения из копии выхода. Переименованная в IDE
форма идёт за файлом событием хоста (`DocumentMoved`, `FormViewModel.MovedTo`). `--reclaim` меняет
типы публичным `SwapAsync` хоста, а не рефлексией. `--probe` снова работает: удержанное поколение
дизайнер не перезапускает, а называет держателя.

| Режим | Вердикт | Время |
| --- | --- | --- |
| `--verify` | ok | 42 с |
| `--stress` | ok | 26 с |
| `--live` | ok, части 1–3 | 66–74 с |
| `--reclaim` ×3 | все три случая «provably dead» | 15 с |

Фазы замены (`CHECK timing`: отпускание, разборка, возврат, преемник). `--reclaim`: случай 1 — 71–98,
4–5, 231–238, 338–385 мс; случай 2 — 98–125, 0, 323–328, 371–380 мс; случай 3 — 84–91, 1, 352–359,
586–609 мс. `--live`: L3 — 39–46, 0, 316–329, 411–431 мс; L4 — замена закончена через 0,9–1,0 с после
отпускания жеста; L5 — 32–35, 0, 308–341, 308–343 мс; L7 — 10–18, 0, 233–350, 304–321 мс; L9 — возврат
не удался за 2,0–2,1 с, а новая копия приняла сессию через 5,4–5,9 с после того, как окно стало
«впереди». Возврат — на уровне этапа 4; отпускание и преемник видны теперь отдельно.

Что нашёл стенд по дороге:

- **Отказавшееся обновление корня оставляло копию окна открытой.** Свойство корня, записанное
  элементом-свойством, — `Design.DataContext` среди них — обновление переносит на корень из копии, а
  узнаёт, что не может, только построив её; тогда оно просит новую сессию и уходило, копию не закрыв.
  На Win32 незакрытое окно переживает любую сборку мусора, и копия с дизайн-экземпляром держала
  поколение: первая же замена после частей 1–2 `--live` (IDE убрала `Design.DataContext`, дизайнер
  вернул) находила типы удержанными. Исправлено в Markup (`2e71ff5`): обновление закрывает всё, что
  построило и не оставило в дереве, каким бы путём ни вышло.
- **Проба держателей не видела полей базовых классов.** `GetFields` отдаёт закрытые поля базового
  класса только при вопросе к нему самому, а контрол держит почти всё — значения, родителя, детей — в
  закрытых полях `AvaloniaObject`, `Visual` и `StyledElement`. Проба останавливалась на первом же
  контроле и отвечала, что поколение не держит никто; теперь она идёт по всей цепочке и называет путь
  — так и нашлась копия: `DevToolsExtensions.s_trackedWindows[]… → MainWindowViewModel`.
- **Проверка не держит ничего от поколения через замену.** В Debug все локали асинхронного метода
  поднимаются в его состояние и живут до его конца: форма или контрол прежних типов в такой локали
  держит поколение. Части 1–2 возвращаются раньше, чем начинается часть 3, а шаги части 3 сравнивают
  тексты, пути и числа; то, что трогает холст, — в отдельных методах без встраивания.
- **Диагностики загрузки писались после сборки хоста.** «Run a restore» стояло под строкой о только
  что сделанном restore, а ошибки сборки заменялись предупреждениями оценки. Теперь консоль говорит в
  том порядке, в каком было: что нашла оценка, потом что сделали restore и сборка.

### После этапа 6 плана (контролы проекта, данные, канал)

Палитра начинается разделом «Project»: контролы проекта впереди и его ссылок, как их перечисляет хост
(`GetPlaceableControlsAsync`, ADR 0031 ProjectSystem), собранные и несобранные. Несобранный бросок
собирает проект (`EnsureBuiltAsync`) и ставит контрол после замены — по именам: файл формы, путь
родителя, индекс (`DropIntent`). Тяга формы контрола из файлов проекта идёт той же дорогой. Правка
разметки размещённого контрола в IDE перестраивает на месте только размещающие его элементы
(`XamlLiveDocument.RebuildAsync` с выбором хоста). Раздел «Data» выбирает тип данных из каталога хоста
(`GetTypeCatalogAsync`), предлагает члены на уровень вглубь, снимает привязку и переименовывает
`x:Name`. Канал отвечает на команды дизайнера (раздел выше); каждую прогнали вживую на копии проекта
`--verify`. Панели диагностик по кодам, которую называл план, нет: вкладки «Problems» в демо нет по
слову владельца, и диагностики с кодами остаются в консоли.

| Режим | Вердикт | Время |
| --- | --- | --- |
| `--verify` | ok | 42 с |
| `--stress` | ok | 26 с |
| `--live` | ok, части 1–4 | 75–76 с |
| `--reclaim` ×3 | все три случая «provably dead» | 15 с |

Фазы замены. `--reclaim`: случай 1 — 66–72, 4–5, 235–250, 200–359 мс; случай 2 — 108–123, 0, 319–331,
245–387 мс; случай 3 — 102–128, 1, 323–357, 447–625 мс. `--live`: L3 — 41–55, 0, 330–342, 406–414 мс;
L4 — замена закончена через 0,97–0,98 с после отпускания жеста; L5 — 35–41, 0, 335–353, 321–330 мс;
L7 — 17–24, 0–1, 228–350, 333–353 мс; L9 — возврат не удался за 2,1 с, новая копия приняла сессию
через 6,05–6,12 с. На уровне этапа 5.

Что нашёл стенд по дороге:

- **Лямбды одного метода делят замыкание.** Бросок несобранного контрола держал поколение всю сборку и
  замену, и замена после L6 находила типы удержанными. `Drop` создавал две лямбды: долгую — ждать сборки
  и поставить по именам — и короткую, захватившую размещение редактора, то есть живые контролы старого
  поколения. Компилятор кладёт захваченное одной области в один объект замыкания, и долгая лямбда
  держала размещение вместе с ним. Бисекция стенда — тот же прогон без броска — возвращала поколение.
  Долгая лямбда теперь создаётся в своём методе (`Place`), куда приходят только имена. По той же
  причине — асинхронный метод держит свои локали до конца — раздел «Data» читает типы поколения и
  просит каталог хоста двумя методами подряд (`FillDataSectionAsync`): запрос каталога ждёт очереди
  хоста за заменой, и ждавший внутри первого метода держал бы его типы через эту замену. Это нашлось
  чтением диффа, а не стендом: стенду для этого нужно, чтобы выбор пришёлся на начало замены.
- **Перестройка содержимого окна теряла обработчики.** Ресурсы, добавленные IDE у корня окна, —
  правка содержимого корня; после неё щелчок по кнопке из этого содержимого не звал ничего. Обновление
  сопоставляло перестроенные элементы с логическими детьми объекта, а у окна Avalonia 12 среди них
  стоит свой `TopLevelHost`, и сопоставление останавливалось у корня; карта находила новые объекты по
  позициям, записанным против текста копии, — на строку мимо. Исправлено в Markup (`0ec49dc`):
  сопоставление читает член содержимого.
- **Контрол проекта встаёт под приставкой.** Фрагмент `<BadgeControl xmlns="using:…"/>` Markup не
  вставлял (`AXM1043`): пространство по умолчанию нельзя переименовать там, где без приставки пишется
  Avalonia. Элемент палитры для контрола проекта несёт приставку — предложенную библиотекой или
  `local`, — а пространством по умолчанию у фрагмента остаётся Avalonia: в нём `FragmentFor` пишет
  место (`Canvas.Left`, `Grid.Row`).
- **Фикстура L9 роняла прежнюю копию на выходе.** Контрол, подписанный на `ProcessExit`, менял
  `IsVisible` из потока выхода, и прежняя копия, уходя после перезапуска, падала с
  `InvalidOperationException` в стандартный поток ошибок. Вердикта это не меняло; теперь он отдаёт
  запись диспетчеру.
